# ADR-013：应用 API 模块化合并与部署边界

- **状态：** Accepted；应用工程边界已实施，Runtime 业务接线仍待后续阶段
- **日期：** 2026-09-23
- **适用阶段：** 当前单节点、受控本地部署的 Web 应用 MVP；后续局域网节点管理以 ADR-026 为准
- **配套设计：** [素材工作台 MVP 工程设计稿](../design/console-mvp.md)

## 1. 背景

SensoryPlex 需要提供带界面的最小应用，完成真实视频导入、模型处理、素材入库、检索和原片回看，
并支持管理员安装、配置、启停和卸载插件。既有 `services/gateway` 提供业务 REST 和鉴权，
REST / MCP / gRPC 是面向业务调用者的协议适配方向；其中 MCP 和对外查询 gRPC 尚未完成服务接线。

业务访问与平台管理有不同的权限、对象和风险，但当前没有两者分别扩容、独立团队发布或分别暴露网络的既定需求。
首版实际推理和插件生命周期仍由独立 Rust Runtime 与插件进程执行。

因此，需要分别决策逻辑模块边界、进程边界和仓库边界，不能仅根据调用者是 Web 还是 Agent 拆服务。

## 2. 决策

1. **同仓库、一个后端工程、首版一个 API 进程。** 目标工程为 `services/api`，从现有 Gateway 迁移，
   不并行维护两套相同业务实现；现有 `/v1` 业务接口保持兼容。
2. **Business 与 Admin 模块分开。** Business 提供素材、业务任务、检索与受控媒体访问；
   Admin 提供插件、Pipeline 发布、节点配置和审计。Web 按功能调用两个模块，Agent 默认只使用 Business。
3. **应用服务与协议适配分开。** REST、后续 MCP / gRPC 调用相同应用服务与授权规则；
   管理路由不会被自动注册为 MCP tools。模块不得互相导入路由实现。
4. **Runtime 保持独立。** API 负责授权、持久接受命令和查询；Rust 负责执行状态、调度、安装、进程托管、
   取消与恢复。API 不在 HTTP 请求中执行安装脚本、导入插件或运行推理。
5. **Registry 保持独立职责。** 首版使用受控的目录和离线产物源，不建设公共开发者发布平台。
6. **跨进程消息仍以 `proto/` 为唯一契约源。** 本 ADR 和配套文档中的字段与接口均为设计输入，
   不能替代后续 Proto 定义与 `make proto`。
7. **Web 是唯一管理入口，不引入桌面客户端。** 当 ADR-026 的局域网 worker 拓扑实施后，主节点的
   Admin 模块负责节点与插件部署意图；子节点 agent 以受认证的管理通道执行操作。浏览器/API 请求
   处理进程仍不得直接在目标主机安装插件或运行推理。

## 3. 权限与隔离边界

- 路由前缀建议为业务 `/v1`、管理 `/admin/v1`，身份会话位于 `/auth/v1`。
- 浏览器使用会话身份，Agent 使用可撤销且有 scope 的凭据；两者最终得到统一的授权上下文。
- 对象权限检查必须在应用服务/查询层执行，检索与媒体读取均校验 owner，不能只限制菜单或列表。
- 管理员身份不自动获得所有用户的素材读取权；管理权限和内容访问权限分别授予。
- 现有静态 token 只能在明确的兼容配置中映射既有业务权限，不能因升级自动变为管理员。
- **同进程共享故障域和可用凭据。** 模块、路由、连接池和限流只能减少耦合，不能构成进程级安全隔离。
- 当前 MVP 默认仅本机回环访问。ADR-026 的局域网子节点只增加受 mTLS/授权保护的 agent 管理通道，
  不等于把浏览器 Console、Admin API 或业务 API 直接公开到局域网或公网；面向远端或公网发布前仍须
  重新评估部署边界。

## 4. 方案比较

| 方案 | 优点 | 代价 / 判断 |
| --- | --- | --- |
| 所有路由和逻辑堆在现有 `app.py` | 改动少 | 权限和依赖混杂，拒绝采用 |
| 一个工程、分模块、一个 API 进程 | 统一发布和身份规则，业务复用直接，便于单机交付 | 共享进程故障域；**首版采用** |
| 两个 API 进程、独立身份和网络 | 可分别暴露、限制权限、升级与扩容 | 增加配置和部署协作；满足拆分条件后采用 |
| 两个仓库、各自维护业务逻辑 | 发布完全独立 | 当前缺少收益，易造成规则漂移，暂不采用 |

## 5. 拆分部署的触发条件

出现下列任一明确要求时，实施两个入口应用和两个进程，而不只是增加 URL 前缀：

- Business 面向公网或独立网络，Admin 只允许管理网络访问。
- Business 进程不得持有插件安装、节点配置或对应数据库/Runtime 权限。
- 管理请求造成的故障或资源竞争已影响业务 API 的可用性，模块配额不足以解决。
- 两类接口有实际不同的扩容、发布周期或运维责任。

拆分时保留 application/domain 模块，分别装配允许的协议入口、数据库角色和 Runtime 身份，
验证负向授权与故障隔离；不能让两个进程仍共用全权限凭据后宣称已实现安全隔离。
拆分进程不自动要求拆分 Git 仓库。

## 6. 后果与验收

- 增加一个独立前端工程 `apps/console`；首版本地发布由 API 同域提供编译后的静态资源。
- 首版无需单独运行 `admin-api`、身份服务或公共 Registry。
- 增加真实身份/权限与审计能力，当前单一 Bearer token 不满足这一要求。
- 安装、上传、查询使用独立配额；重任务在 Runtime，API 进程重启不丢失已接受命令。
- 用负向测试确认业务凭据不能调用管理操作，MCP 工具清单不含管理能力，素材读取不能越权。
- 用真实样本验收业务闭环；本 ADR 的存在、接口返回 202 或健康检查通过均不代表闭环完成。

## 7. 与既有设计的关系

本 ADR 补充[技术蓝图](../../技术选型ADR与V1实施蓝图.md)中的 Gateway 部署方式，
不改变 Rust 运行时、Python 模型插件、控制面/媒体数据面分离和不可变事实约定。
它仅规定新的应用 MVP 如何组合接口，不代表现有 `services/gateway` 已被重命名或新增模块已经可用。
局域网插件 worker 的主/子节点拓扑、数据本地性、安装状态与验收要求由
[ADR-026](ADR-026-Web主节点与局域网插件worker拓扑.md) 补充；当前实施状态仍以单节点为准。
