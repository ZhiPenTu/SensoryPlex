# ADR-029：可编排插件执行核心（Pipeline DAG、Run/Task 状态机与受控调度）

## 1. 背景与问题

当前工程已经有四类可复用的执行积木：版本化插件 manifest、gRPC `Start/Process/Cancel/Drain/Stop`、
Runtime 数据面 lease、节点 Registry 与插件部署意图。`tools/ai_worker.py` 也能在授权样本验收中发现
输入、调用**一个**插件并收集 Observation。

它们不构成编排：Pipeline YAML 中的 `processors` 仍是声明性列表，Console 只能保存方案与任务草稿；
Runtime `serve` 不运行 Pipeline，`POST /v1/jobs` 与 Pipeline publish 都明确拒绝。把几个 CLI 进程按顺序
启动的做法没有持久 Run、依赖、资源决策、失败恢复或取消账目，不能作为产品路径。

本 ADR 把缺口收束成一个核心：主节点 Runtime 内的 **Orchestrator**。它只编排受控插件的执行，不取代
GStreamer 数据面、Timeline 事实融合、索引 sink 或 Gateway 的鉴权。

## 2. 决策

### 2.1 以不可变 Pipeline revision 编译 DAG

发布前把 Pipeline 定义编译为 DAG；运行时绝不解释可变草稿。图中每个节点必须声明：

- 稳定身份：`node_id`、`plugin_id`、插件版本、artifact digest、config hash；
- 类型与边界：`source`、`processor`、`sink` 或 `control`；
- 输入/输出 modality、时间关联与 batch/ordering 约束；
- placement：`data_plane_local`、`same_node_as:<node>`、`object_ref_allowed` 或显式节点约束；
- deadline、最大 attempt、优先级和资源声明的引用。

每条边都要声明 `from`、`to`、modality、半开时间范围 join 策略和是否为可选慢路径。编译器必须在创建
revision 前拒绝：环、悬空端点、重复 ID、不相容 modality、跨机 lease、未解析插件版本、无上限重试、
未声明的可选/必需输入，以及容量超过节点档位的图。

YAML/Console 表单只是 authoring format；跨进程传递、持久化与 worker 指令的唯一契约在 `proto/`。
不得通过任务 payload 传入 Python import 路径、可变镜像 tag、宿主路径、帧/音频字节或密钥。

### 2.2 主节点是唯一调度权威

每个部署仅有一个活跃 Scheduler。API 在事务中接受命令、写入事实与 outbox；Scheduler 认领已持久化
的 Run/Task 并产生命令。浏览器、API 请求线程、插件进程和节点 Agent 都不能自行修改任务依赖或选择
另一台节点执行。

调度选择按以下硬约束顺序进行：

1. 输入可达性与数据外发策略；
2. Runtime lease / 共享内存 / GPU 句柄的同机性；
3. 用户或 Pipeline 的显式节点约束；
4. 插件协议、不可变 artifact 与配置兼容性；
5. 已报告的执行后端、资源预算、并发与队列余量；
6. 只有前五项都满足后才考虑性能偏好。

找不到合法位置时，任务进入 `blocked` 或 `failed` 并记录稳定 `reason_code`。不允许把“目标节点离线”
悄悄变成“随便找一台能跑 CPU 的机器”。只有 Pipeline 显式允许的 failover 策略，才能产生新的 assignment；
原 assignment 保留完整审计记录。

### 2.3 状态机先于消息投递

至少一次消息投递不是任务真相。`pipeline_run` 与 `pipeline_task` 是 PostgreSQL 的事实，JetStream 只承载
由 outbox 确认发布的命令/状态通知。终态不可倒退，所有迁移以行锁或 compare-and-set 保护。

```text
PipelineRun: accepted → validating → queued → running
              ├────────────────────────────→ succeeded
              ├────────────────────────────→ failed
              ├────────────────────────────→ cancelled
              └────────────────────────────→ expired

Task: pending → ready → assigned → running → succeeded
                         │          ├──────→ retry_wait → ready
                         │          ├──────→ failed
                         │          └──────→ cancelled
                         └─────────────────→ blocked
```

- 下游仅在其所有必需上游 `succeeded` 且输出契约通过后变为 `ready`；可选慢路径失败只能产生明确的
  `partial`/enrichment 状态，不能把必需素材伪装成 `fast_ready`。
- `Cancel` 从 Run 传播到未完成 Task；已经调用插件的 Task 必须接收同一 request identity 的 `Cancel`，
  并在 grace period 后标为 `cancelled` 或 `cancel_timeout`，不是直接删除记录。
- 只对 `retryable=true` 且尚有预算的失败重试；每次 attempt 有新的 delivery ID、相同语义
  `idempotency_key`。预算耗尽写 `retry_exhausted`，不无限重投。
- Scheduler 崩溃或 assignment lease 到期后，恢复器检查 worker 的最终事实：已确认结果收敛为成功，未知
  的在途 Task 才按幂等键重派或失败。不得依据“没有收到回调”直接重复写 Observation。

### 2.4 数据面与控制面严格分离

`BufferDescriptor` 只能在签发它的同机 Runtime/worker 数据面中使用。任务消息可引用 descriptor 的
受控 ID，但不携带 locator 指向的字节；从 Scheduler 到远端节点的消息不能让远端映射本机共享内存。

跨节点仅允许两种输入：已经持久化并授权的 Observation，或策略允许的受控 object reference。若图边需要
raw buffer 而没有同机候选，编译/调度必须以 `data_locality_violation` 拒绝。这样可以保持现有 lease、
TTL、释放和容量账目有效，而不把“编排”变成越权数据搬运。

### 2.5 Node Agent 执行真实生命周期，Plugin 不获得调度权

Agent 接到的部署/运行意图必须验证 artifact digest、配置 hash、签名/策略状态和节点能力；随后才启动或
drain 受控进程，并用 `Describe`、`ValidateConfig`、`Start`、`Health` 的事实回报更新实例状态。当前只回报
状态的 agent 行为不能充当本 ADR 的完成证据。

插件只收到已经授权的 `Process`/`Cancel` 调用，绝不收到数据库凭据、NATS 管理权限、其他插件私有内存或
“下一步调谁”的控制权。插件产出的 Observation 经过契约校验后才解锁下游 Task。

## 3. 契约与持久化边界

新增或扩展的 Proto 以 `proto/orchestration/v1/` 为唯一源，至少覆盖 `PipelineRevision`、`PipelineNode`、
`PipelineEdge`、`PipelineRun`、`PipelineTask`、`TaskAssignment`、`TaskResult`、`CancelTask` 和稳定 reason code。
生成代码一律由 `make proto` 产出，禁止编辑 Rust/Python/Console 的生成物。

数据库迁移仅追加，至少新增 `pipeline_definition`、`pipeline_revision`、`pipeline_run`、`pipeline_task`、
`pipeline_task_edge` 与 `scheduler_assignment`。必须有以下不变式：

| 不变式 | 约束 |
| --- | --- |
| 已发布图不可变 | `graph_digest`、定义 JSON、节点 artifact/config hash 不可原地更新 |
| 幂等 | 同一 revision + input_ref + idempotency key 至多创建一个活动 Run |
| 下游解锁 | 必需上游未成功时，Task 不得进入 `ready` |
| 结果归属 | Result 的 run/task/attempt/assignment 与签发记录完全一致才可落状态 |
| 取消优先 | 已取消 Run 不得解锁新 Task；迟到成功结果单独审计，不改回成功 |
| 资源可见 | assignment 必须记录请求/实际节点、数据面节点、预算快照与拒绝原因 |

## 4. 分阶段交付

| 阶段 | 交付 | 明确不声称 |
| --- | --- | --- |
| P0 编译内核 | Proto、DAG 编译器、图/placement 校验、Run/Task 状态机与确定性单测 | 不调插件、不启动 worker、不称为可执行 Golden Path |
| P1 单节点执行 | PostgreSQL Run/Task、outbox 命令、同机 Runtime + 一个真实 processor 的 `Start/Process/Cancel`、重试/取消/恢复 | 不自动跨机改派、不支持任意图节点 |
| P2 受控多节点 | 真 Agent 生命周期、node capability/资源选择、object-ref 跨机分支、审计回滚 | 不支持共享内存跨机、不做多主调度 |
| P3 产品闭环 | Console 发布/提交/取消/详情，真实文件 → OCR/VLM → Timeline → 索引 → API 检索 | 不以健康检查或合成 Observation 代替 E2E |

P0 之前，现有 `tools/ai_worker.py` 仍是验收工具，不得接入 Console 作为生产任务执行器。

### 4.1 核心产品能力要求

P1–P3 不是可选路线图，而是本 ADR 定义的可复用底座能力。只有达到 P3，第三方才能在不改 Runtime
核心的前提下，把受控插件与已发布 Pipeline 组合成一个可安装、可升级、可审计的场景产品。

| 阶段 | 强制需求 | 通过条件 |
| --- | --- | --- |
| P1 | 迁移必须追加并持久化 revision/Run/Task/edge/assignment；状态变更、幂等、取消和 lease 由事务保护；API 以 `pipelines:manage`、`jobs:write`、`jobs:read` 授权；outbox 只在事务提交后下发同机 `Start`/`Process`/`Cancel` | 一份真实授权媒体经 Runtime descriptor 被 OCR 或 VLM 实际处理，重复 delivery、retry、取消和 worker 崩溃恢复都能从持久账目复核 |
| P2 | Agent 必须以已验证的 artifact digest/config hash 执行真实生命周期；Scheduler 按数据本地性、策略、能力、资源和 lease 选择节点；跨机仅传 Observation 或受控 object reference | 跨机 descriptor、离线节点、资源不足与 artifact 漂移均显式拒绝/阻塞；仅在 Pipeline 显式允许时产生可审计 failover assignment |
| P3 | 场景产品包必须锁定插件制品与 Pipeline revision，携带配置 schema、RBAC/外发策略和升级/回滚说明；Console/API 支持其发布、提交、取消、查询和可观测性 | 在隔离项目或租户中安装场景产品包后，真实输入经插件链路形成可鉴权查询结果并回跳同一时间窗口；产品方可查看配额、失败与审计 |

P1 未完成前不得对外声称“可执行编排”；P2 未完成前不得声称“跨节点编排”；P3 未完成前不得声称
“可由第三方基于底座交付场景产品”。插件目录、Pipeline YAML、节点心跳、健康检查或单插件回放均不是
这些声明的替代证据。

## 5. 验收与可观测性

每阶段必须补充真实执行证据。P1/P3 的最小真实样本闭环为：授权文件由 Runtime 解码，调度器把同机
descriptor 投递给 OCR 或 VLM 插件，Observation 解锁 Timeline，事实/outbox 进入常驻 index，最后经 API
查询命中对应素材与时间范围。

必须覆盖：环/坏 modality/坏 placement 在发布前拒绝；同机 lease 被拒绝跨机；资源不足排队或稳定失败；
worker 在 Process 中崩溃后的恢复；重复 delivery 不重复产出；取消没有新下游；可重试失败恰好重试到上限；
非 retryable 失败不重试；节点 failover 只在策略允许时发生且留下两次 assignment 账目。

监控至少按 Run/Task/node/plugin/reason 输出吞吐、队列等待、attempt、重试耗尽、取消、assignment 拒绝、
lease 到期与端到端延迟。日志和事件中不得出现原始内容、控制面密钥、私有路径或未脱敏文本载荷。

## 6. 后果与非目标

这项能力会增加 Proto、迁移、恢复逻辑与验收成本，但它将插件扩展从“手工串脚本”变成有证据的产品行为。
它不引入 Airflow、Temporal、Ray、Kubernetes 或一个可执行任意代码的通用工作流引擎；这些系统不会自动满足
本项目的 lease、时间锚点、数据本地性和媒体背压语义。如需替换内部调度实现，必须保留本 ADR 的契约与
不变式，并另起 ADR。
