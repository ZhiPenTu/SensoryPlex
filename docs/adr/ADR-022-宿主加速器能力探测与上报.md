# ADR-022：宿主加速器能力探测与上报（三态、只写真值、与进程能力分离）

**状态：** Accepted（2026-09-24）

**相关文档：** [实现状态](../implementation-status.md)、[验证记录](../verification.md)、[待办](../TODO.md)、[契约与查询语义](../contracts/README.md)

## 1. 背景与问题

ADR-012 §"未验证范围"、ADR-016 §9、ADR-017 §8 与 `docs/TODO.md` 记的是同一个缺口：
`capability::backends()` 把所有后端（含 `coreml` / `metal`）一律记为
`execution_backend_not_implemented`。改动前的事实是：

| 事实 | 位置 |
| --- | --- |
| `backends()` 对 `backend_names()` 的每一项都填同一个 `BACKEND_UNAVAILABLE_REASON`，`runtime_version` / `precisions` / `memory_kinds` 全空、`max_concurrency=0` | `crates/runtime/src/lib.rs` 的 `capability` 模块 |
| `crates/execution` 只有 `ExecutionBackend` trait 与 `Capability` 结构，**没有任何实现**——"本进程不做推理"是真事实 | `crates/execution/src/lib.rs` |
| Apple Silicon 上 `backend_names()` 给出 `cpu, coreml, metal`，三条**结论完全一样** | 同上 |
| 报告里读不到"这台宿主到底有没有这块加速器" | 整个 `DescribeCapabilitiesResponse` |

于是有一句极易被读错的话：报告里 `coreml` 是 `Unavailable`，读的人会顺势理解成
**"这台机器没有 CoreML"**。但这份报告从来没有探测过宿主——它只说了"Runtime 自己不执行推理"。
两件事被塌在同一个字段里：

1. **本进程能不能执行推理**（= 不能，本版本没有任何 in-process `ExecutionBackend`）；
2. **这台宿主有没有这块加速器**（= 从来没测过）。

塌在一起的代价是不对称的：既可能把宿主真有的 CoreML 谎报成没有，也可能让下一个人为了
"让 coreml 变成 available"去动 `backends()`——那等于用一个假事实（"运行时会推理"）换掉另一个缺口。

## 2. 决策一：宿主加速器与执行后端是**两张表**，谁也不替谁说话

`DescribeCapabilitiesResponse` 新增 `repeated HostAccelerator host_accelerators = 7;`（ADR-022 契约）：

- `backends` 仍然回答"**本进程**能不能执行推理"，本切片**不改**它的语义，仍然全部 `Unavailable`
  + `execution_backend_not_implemented`；
- `host_accelerators` 回答"**这台宿主**有没有这块加速器"，是本切片新加的探测结果。

两条必须写死的语义：

- **宿主报 `available` 绝不等于本进程在用它跑推理。** 因此 `model_inference` 继续留在
  `unavailable_capabilities` 里，`state` 继续是 `degraded`；两个字段同时出现不是矛盾，是要点。
- **`backends` 也不许反过来替宿主说话。** 判据是"同一个进程是否有实现"，不是"宿主有没有硬件"。

## 3. 决策二：三态，**探测不到 ≠ 不存在**

`enum AcceleratorState { UNSPECIFIED=0; AVAILABLE=1; UNAVAILABLE=2; UNKNOWN=3 }`。

| 取值 | 含义 | 例 |
| --- | --- | --- |
| `AVAILABLE` | 探测**读到了**宿主事实 | `metal=available(metal4)` |
| `UNAVAILABLE` | 探测成功，宿主**明确报告没有** | `host_reports_no_metal_family`、`framework_absent:CoreML.framework` |
| `UNKNOWN` | 探测**没能给出答案** | `probe_tool_missing:system_profiler`、`probe_timed_out:plutil`、`displays_json_unparsable` |

`UNKNOWN` 是独立取值，不是 `UNAVAILABLE` 的别名，也不是"默认值"。所以：

- `state == ACCELERATOR_STATE_UNSPECIFIED` 不允许出现在报告里；
- `state != AVAILABLE` 的每一条都**必须**带 `unavailable_reason`；`AVAILABLE` 的那条**不允许**带；
- 原因串必须自带来源（`probe_tool_missing:<source>`），否则读的人分不清"工具不在"与"宿主没有"。

混掉的后果是具体的：把"`nvidia-smi` 不在 PATH"记成 `UNAVAILABLE`，会让人以为这台机器没有 GPU，
从而去做错误的技术选型；反过来把"框架不在"记成 `UNKNOWN`，会让真正的缺失永远查不出来。

## 4. 决策三：只写真读到的值，且有界

- `runtime_version` 与 `evidence` 只能来自探测输出。读不到就留空——**不填"看起来合理"的版本号**。
  `evidence` 只保留受控事实（`sppci_model=…`、`cf_bundle_version=…`、`spdisplays_mtlgpufamilysupport=…`），
  **不写文件系统路径、不整段转发工具输出**（AGENTS.md 的日志/控制面约束）。
- 唯一一处改写是 Metal：`runtime_version` 放家族名（`metal4`），带 `spdisplays_` 前缀的原始枚举令牌
  留在 `evidence` 里。这样消费方不必自己剥前缀，而"宿主到底写了什么"没有被抹掉。
- **探测有界**：`PROBE_TIMEOUT = 3s`，超时即 `kill` 并落 `UNKNOWN`。探测工具卡住不能拖住
  `DescribeCapabilities`。

## 5. 探测口径（按目标平台）

| 平台 | 加速器 | 探测 | `detection_source` |
| --- | --- | --- | --- |
| `macos-aarch64` | `coreml` | `/System/Library/Frameworks/CoreML.framework` 在 → `plutil -extract CFBundleVersion raw` | `framework_info` |
| `macos-aarch64` | `metal` | `system_profiler -json SPDisplaysDataType` → `spdisplays_mtlgpufamilysupport` | `system_profiler` |
| `linux-x86_64` | `cuda` | `nvidia-smi --query-gpu=name,driver_version --format=csv,noheader` | `nvidia_smi` |
| 其它 | — | 不报任何条目（`expected()` 为空） | — |

**判定只认 JSON 的键名，不认值。** macOS 会本地化显示文本（`LANG=zh_CN` 下同一份报告的显示文本会变），
但 `spdisplays_*` / `sppci_*` 是稳定标识符，所以判定与语言环境无关——这一条是被单独验收的（§6 路径②）。

CoreML 分两步（框架在 → 再读版本）是为了让"框架不在"（宿主的确定事实）与"版本读不出来"（这次没探到）
给出**不同**结论。`expected()` 只覆盖本表；表外的名字（例如 proto 注释里保留的 `tensorrt`）
**不会**被上报——没有探测路径的名字不该出现在报告里。

## 6. 验收（`make accelerator-check`）

`tools/verify_accelerator_report.py` 起真实 `sensoryplex-runtime serve`，与**独立解析**的宿主实况四路对账。
本机（Apple M2 Max / `macos-aarch64`）实测：

| 路径 | 断言 | 实测结果 |
| --- | --- | --- |
| ① 基线与宿主直读 | 状态与版本逐条等于 `system_profiler` / `plutil` 的直读值；证据无路径、有界 | `coreml=available(3520.5.1)`、`metal=available(metal4)`，版本与直读逐字一致 |
| ② `LANG=zh_CN.UTF-8` | `(accelerator, state, runtime_version)` 三条目完全不变 | 与基线相同 |
| ③ `PATH=/nonexistent` | 工具缺失者必须落 `UNKNOWN` 且原因是 `probe_tool_missing:<source>`，**不许**落 `UNAVAILABLE` | `coreml=unknown`、`metal=unknown` |
| ④ 与执行后端分离 | 同一份报告里 `backends` 仍全部 `unavailable` 且带原因 | 3 条后端全 `unavailable`，加速器表不覆盖它 |

另外：`make runtime-smoke` 现在会打印并断言加速器行
（`host accelerators=[coreml=available(3520.5.1), metal=available(metal4)]`），
`crates/runtime` 单测覆盖解析器与三个探测函数的分支（含"工具缺失 → `UNKNOWN`"与"超时被 kill"），
`tests/contracts/test_runtime_capabilities.py` 覆盖契约面三态与形状。

**顺带修掉的既有缺陷：** `make runtime-smoke` 在本机（容器模式）**必然失败**——被验收的进程是主机构建的
Mach-O 二进制，Linux 容器 `exec` 不了它（`Exec format error`）。现在这一步与 `embed-check` /
`parallelism-check` 同类，固定在主机侧执行（`PY_HOST`）。

## 7. 后果与仍未验证范围

- 交付物：`proto/runtime/v1/runtime.proto`（`AcceleratorState` / `HostAccelerator` / `host_accelerators`）、
  `crates/runtime/src/accelerator.rs`、`capability::describe()` 的接线、`main.rs` 的启动日志、
  `tools/verify_accelerator_report.py` + `Makefile` 的 `accelerator-check`、`tools/smoke_runtime.py` 的断言、
  契约测试与 `crates/runtime` 单测。
- **仍未验证（不得当作完成）：**
  - **`linux-x86_64` 的 `cuda` 分支从未在真机上跑过**：只有夹具单测（`"NVIDIA GeForce RTX 4090, 550.54.14"`），
    没有 NVIDIA 主机的 `make accelerator-check` 记录，也没有带 GPU 的 CI job。远端 `check` job 是
    ubuntu 无 GPU runner，那里 `cuda` 只能是 `unknown(probe_tool_missing:nvidia_smi)`。
  - **`linux-aarch64` 没有任何探测路径**（`expected()` 为空 → 报告里 0 条），不是"已验证没有加速器"。
  - **Mac mini / 跨机未验证**：本切片只在开发机 `macos-aarch64` 上实测。Mac mini 是明确的端侧目标
    （ADR-008），它的报告需要单独跑一次 `make accelerator-check` 才能当作已验收。
  - **`tensorrt` 只存在于 proto 的命名说明里**，没有探测路径、也不会被上报。
  - **加速器可用 ≠ 推理可用**：本版本仍无任何 in-process `ExecutionBackend`，
    `model_inference` 继续在 `unavailable_capabilities` 中；插件侧的后端选择（ADR-016 / ADR-017）
    与本表**不共享数据**，本切片不改变插件行为。
  - `metal` 的 `runtime_version` 是 Metal **家族令牌**（`metal4`），不是 OS/Xcode 版本；
    `coreml` 的是 CoreML framework 的 `CFBundleVersion`，两者语义不同名，不得横向比较。
  - 探测是**启动后首次 `DescribeCapabilities` 时**做一次并缓存（`OnceLock`），不是持续监控：
    热插拔 eGPU、系统升级后不重启进程都不会刷新。
