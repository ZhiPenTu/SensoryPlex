# ADR-027：事件链路的分级背压准入与容器化常驻（relay / index 进 compose）

**状态：** Accepted（2026-09-24）
**上游决策：** ADR-019（运行时消费分级队列上限：准入，而不是改写）、ADR-024（outbox 分发接线与消费去重边界）、ADR-025（常驻消费循环与 sink 接线）、ADR-020（向量索引落库与检索闭环）、ADR-015（macOS 常驻形态与统一内存分级）、ADR-010（跨进程数据面的安全边界）
**相关文档：** [实现状态](../implementation-status.md)、[验证记录](../verification.md)、[待办](../TODO.md)、[契约与查询语义](../contracts/README.md)

## 1. 背景与问题

ADR-019 把"分级是**准入上限**，不改写也不夹取"写成了规则，但它只落在**媒体面**
（Rust 的 `replay` / `ingest`）。事件链路那一侧的缺口被 ADR-025 §11 原文记着两句：

1. *"吞吐与背压未测：单批串行、在飞恒为 1，ADR-019 的队列上限没有接到这一层"*；
2. *"消费侧与 relay 都还没有进 compose：常驻形态靠 `make outbox-run` / `serve --consume` 显式起"*。

于是有两处"看起来在跑"，而且都不会报错：

| 坏结局 | 事实 |
| --- | --- |
| **上限形同虚设** | 16 GiB 机型的 `resident.env` 说事件链路上限 16，但 relay 的 `--batch` 默认 **200**（上限 1000）、消费的 `--consume-batch` 默认 **50**（上限 500，且它就是 `max_ack_pending`）。两台机器可以跑出一样的状态行，而真实在飞深度差一个量级。 |
| **"容器在跑"被读成"链路在通"** | 没人把两个常驻服务放进同一份 compose 里跑过。健康检查成功、进程活着，都回答不了"事件真的从 outbox 走到了向量库、并且能被检索到"。 |

本切片回答的就是这两件事：**分级上限怎么接到事件链路**，以及**两个常驻进程怎么进 compose 并证明链路是通的**。

## 2. 决策一：分级表新增一列"事件链路"，不复用媒体队列那个数

`tools/macos_resident.py` 的 `Tier` 增加 `event_queue_capacity`，`resident_env_text()` 导出
`SENSORYPLEX_EVENT_QUEUE_CAPACITY`，`tier_values()` / `summarize()` 同步：

| 档位 | `media_queue_capacity` | `event_queue_capacity` |
| --- | --- | --- |
| `small`（16 GiB） | 16 | 16 |
| `medium` | 32 | 32 |
| `large` | 64 | 64 |
| `xlarge` | 128 | 128 |

四个档位**今天同值**，所以它看起来像一次重复。刻意不改成一个字段的理由：

- 没有证据说明"媒体保留窗口的深度"与"事件在飞的上限"必须相同——它们约束的是两种完全不同的东西
  （内存里的帧字节 vs 队列里未确认的消息）；
- 复用会让"调媒体队列"顺手改掉事件链路，而**没有任何地方显示这件事发生过**；
- 分化只需要改这一张表（改完 `resident.env` 就是新的），不需要动任何进程。

同一句话在 ADR-019 里已经写过一次：分级是**单一事实源**，值是渲染出来的、不是各处猜出来的。

## 3. 决策二：准入读环境、判定在进程里，越界拒绝启动

新增共享模块 `services/outbox-relay/src/sensoryplex_relay/residency.py`。它**放在 relay 包内**是因为
两边都要用它，而 `index-worker` 已经依赖 relay 的 `contract.py`（事件契约的唯一实现）；
反过来放会让依赖成环。

三种输入、三种结果（与 ADR-019 §3 逐字对齐）：

| 输入 | 结果 |
| --- | --- |
| `SENSORYPLEX_EVENT_QUEUE_CAPACITY` 缺失 | `not_injected`：`inflight_capacity=0`，**绝不**填一个"看起来合理"的默认值 |
| 空串 | `invalid_resident_limit: <VAR> is set but empty` —— 设置了空串 ≠ 没设置 |
| `0` / 非数字 | `invalid_resident_limit: <VAR>=<value>` |
| 声明值 > 上限 | `event_inflight_exceeds_tier_cap: declared=<n> tier_capacity=<n> tier=<name>` |

- **原因串与 Rust 侧逐字相同**（`crates/runtime/src/lib.rs::parse_resident_limit`，含
  `is set but empty` 这个措辞）：运维不该按"这个进程是哪种语言写的"去记住两套码；
- **判定对象是两个声明值**：relay 的 `--batch`（每轮认领深度）与消费的 `--consume-batch`
  （`max_ack_pending` = 在飞未 ack 的深度）。上限就是"这一档允许的在飞上限"；
- **失败位置在连任何东西之前**：relay 在读 `--database-url`/连库之前、index 在**抢向量库的锁之前**。
  坏配置要先崩在配置上，而不是带着一个注定被放大的深度去占别人的目录；
- **失败形态是原因码退出**（`SystemExit` 的字符串），不是 traceback；
- **为什么不是夹取**：夹取会让 `.env` 里写的数与状态行里报的数长期不一致，而这两个数恰好是背压的
  分子与分母。这与 ADR-019 §2 拒绝夹取、拒绝改写是同一个理由。

## 4. 决策三：两个进程各自判定，不共享一个令牌桶

relay 的在飞是"**已认领、未发布**"，消费的在飞是"**已投递、未 ack**"。这是**两段不同的在飞**，
各有各的上限、也各自可能成为瓶颈：

- 合成一个计数器等于把两件事抹成一个数：relay 卡在 NATS 上会让消费侧显示"满了"，反之亦然；
- 共享令牌桶需要一个跨进程协调点（新的常驻组件、新的失败形态：协调点挂了算谁的责任？）。
  本切片不引入它——真要合并这两个数，那是一次独立的决策，不是这里的顺手改动。

## 5. 决策四：状态行里多四个字段，未注入是显式事实

`relay.status` 与 `consume.status` 都新增 **4 个字段**：

| 字段 | 含义 |
| --- | --- |
| `inflight_state` | `admitted` / `not_injected`（只有这两个取值，不发明"看起来在跑"的中间态） |
| `inflight_declared` | 本进程的声明深度（relay = 每轮认领，index = 在飞未 ack） |
| `inflight_capacity` | 本档上限；`not_injected` 时为 `0` |
| `resident_tier` | 档位名；没注入时为 `not_injected` |

`not_injected` 是**显式事实**而不是"上限为 0 条"：开发机没有 `resident.env` 时，读的人必须能看出
"这一层没有被分级管着"。这 4 个字段只有状态字符串、整数与档位名——不加端点、路径、令牌或载荷。
`--describe` 与 `serve` 的就绪行里同步给出，所以"这个进程按哪个档、上限多少"不需要去翻日志。

## 6. 决策五：常驻进 compose —— 独立 profile、仓库 bind mount 的 `.data/`、会动的健康检查

`deploy/compose/docker-compose.poc.yml` 新增两个服务（`relay` / `index`），并由
`deploy/up-events.sh` / `deploy/down-events.sh` 起停：

| 决策 | 理由 |
| --- | --- |
| `profiles: ["events"]` | 默认栈（`./deploy/up.sh`）不拖起 BGE 权重与向量库；`make events-up` 才起 |
| 复用 `sensoryplex-api:0.1.0` 镜像与仓库 bind mount | relay / index 的包已在 api 镜像里（同一份依赖），不为两个进程再建两个镜像；bind mount 让源码与容器看到的是同一份 |
| 向量库落 `.data/index/milvus.db`（**不是命名卷**） | 命名卷的挂载点是 root 所有，而容器以非 root 用户运行 → `PermissionError: [Errno 13]`（本切片真踩过）。`.data/` 已被 `.gitignore` 排除 |
| relay 健康检查 = 状态行 mtime < 15s | 每轮都会重写状态行；**停在那里的 relay 不该被读成在跑** |
| index 健康检查 = TCP 连 50077（`start_period: 60s`） | 端口在**编码器与向量库契约之后**才开（模型起不来 / collection 漂移都开不了端口），但**早于**消费侧接上。所以"能连上"只说"检索面就绪"；"消费真的接上了"的凭据是 ready 行——它在 `runner.wait_ready` 确认之后才写（本切片顺手把这次 `_emit` 从"开端口之后"挪到了"确认之后"，免得造出"文件说消费在跑、进程还没接上"的窗口） |
| api 顺带接上检索面（`index:50077` + 令牌） | 这是 ADR-023 那一跳在 compose 里的最后一公里；令牌在 `.env` 里有两个名字（检索面读 `AUTH_TOKEN`、api 读 `SEARCH_TOKEN`），`tools/configure.py` 用**一次** `replace` 把同一个随机值写进两处——"两个名字两把锁"是这里要避免的失败形态 |

`up-events.sh` 的前置检查是**显式失败**：`.env` 缺失、BGE 权重目录缺失（`MODEL_DIR/onnx/model_quantized.onnx`）
都打印固化命令后退出，**不联网下载**。`down-events.sh` 用 `rm -sf relay index` 只收这两个服务
（不用 `down`，避免顺手拆掉 api / postgres），`--volumes` 时删 `.data/index`。

## 7. 决策六：验收在容器内、并用真实 HTTP 收口

`make event-pipeline-check`（`tools/verify_event_pipeline.py`，**api 容器内**执行）与
`make consume-check` 分工不同，两条都要有：

| 目标 | 位置 | 验的是什么 |
| --- | --- | --- |
| `make consume-check`（ADR-025） | 主机 | **单进程内**的消费正确性：fail-stop、重放去重、目录锁、三类启动期显式失败（Milvus Lite 目录与 BGE 权重只在主机） |
| `make event-pipeline-check`（本切片） | 容器内 | **两个常驻服务真的在 compose 里把链路跑通**，并用真实 HTTP 语义检索收口 |

判定（全部来自真实执行，脚本不自己起 relay / index）：

- 两个状态行的准入必须是 `admitted`、同档位、同上限，且声明值 <= 上限；
- 一条**越界**配置喂给**真实** relay CLI：必须在连数据库之前按 `event_inflight_exceeds_tier_cap` 拒绝
  （不夹取、不静默降级）；
- `published_total` / `consumed_total` 必须**各自增长**（计数器单调 → 比较本次增量，
  而不是"状态文件还在"）；
- `embedding_record` 出现 ready 行，带 `vector_ref`（受控引用）/ `indexed_at` / `model_release_id`；
- `POST /v1/materials:search` 的 `mode=semantic` 返回该素材，并且它**排第一**（不是"返回点什么"）；
- 删掉事实行后同一个查询不再返回它，陈旧向量计入 `unindexed_hits`；
- 本次写入的行全部清干净（对该脚本留下的每一行按标记回收），且状态行与响应不外泄
  （DSN / 主机路径 / 令牌）。

## 8. 已知残余（本切片刻意不修，必须写出来）

1. **向量本体不随事实行删除而消失**。ADR-020 §2 的回查挡住了"陈旧向量被当成事实返回"，
   但向量库里的行还在。于是验收脚本**每次运行都会留下 2 条陈旧向量**，`unindexed_hits` 会累积。
   脚本因此用**本次运行唯一的批次标记**写文本与查询（当前批次的向量必然排进窗口最前，不会被上一轮
   的残留挤掉），判定写成"**相对基线**"而不是"绝对为 0"，并在通过时如实打印留下了几条。
   **这条残留会改变产品行为，不只是验收噪音**：陈旧向量占的是同一个 `limit` 窗口，所以随着累积，
   同一个查询能返回的真实素材会变少——实测中"相关 + 无关"两条素材的命中数从 2 掉到 1
   （无关的那条被陈旧向量挤出了窗口），而排名与 `unindexed_hits` 的相对变化没有变。
2. **向量 GC 未做**（按 `material_unit_id` 删除 / 按 `indexed_at` 回收）：它需要 Milvus 的 delete 语义
   与一条新的保留策略决策，是独立切片。想从干净向量库重跑用 `./deploy/down-events.sh --volumes`。
3. **吞吐未测**：本切片接的是**准入**（在飞深度的上限），不是"吞吐达标"。乘起来的两个因子
   （relay 每轮 16、消费在飞 32）只在 `medium` 档跑过，没有吞吐/延迟曲线。

## 10. 顺带修掉的缺陷（真跑出来才看见）

1. **契约与集成测试被宿主环境绑架**：api 容器现在**真的**配了检索面，于是
   `Settings(database_url=...)` 的默认值随环境变——`tests/contracts/test_semantic_search_contract.py`
   与 `tests/integration/` 里三个"未配置检索面"的用例在容器里立刻变红。这不是"测试太严"，而是
   **用例没有自己控制环境**：`Settings` 会读进程环境**和**仓库 `.env`。
   新增 `tests/conftest.py::bare_settings`（`_env_file=None` + 摘掉 `SENSORYPLEX_INDEX_SEARCH_*`），
   断言"未配置 / 半配置会被拒绝"的用例改用它。**环境替用例做决定，验的就是宿主机**——
   而这个探针那次是有价值的：它证明这条断言确实在依赖环境，只是依赖得不对。
2. **准入必须落在能被捕获的位置**：`consume_options_of` 原本在 `run_serve` 的 `try` 之外被调用。
   它新增的准入检查抛的是 `ResidencyError`（不是 `ConsumerError`），放在外面就会冒成 traceback
   而不是原因码退出。现在参数越界与分级准入共用同一处
   `except ResidencyError → SystemExit(code)`，两者的失败位置也确实是同一处（都在抢向量库之前）。
3. **空串配置会让 api 拒绝启动**（容器编排的必然产物）：`${SENSORYPLEX_INDEX_SEARCH_TOKEN:-}` 只能
   给出**空串**、给不出"这个变量不存在"，而 `Settings.validate_index_search` 原本把"令牌是空串"
   读成"配置了一半" → 于是**任何早于本次改动的 `.env`**（`make configure` 生成后不再覆盖）都会让
   api 起不来，整个栈挂在一个与事件链路无关的配置项上。本切片第一次写 compose 接线时把 api 的
   终结点**硬编码**成 `index:50077`，正是它把这个陷阱变成"必然"（终结点写死 + 令牌缺省 = 半配置）。
   现在终结点也取自 `.env`（缺省即空），且**空白读成没配**（`index_search_endpoint=""` /
   `index_search_token=None`）——**半配置仍然被 `*_required` 挡住**，契约测试补了三条断言，
  两条路径都在容器里复测过（空白 → 正常启动且 `semantic_search` 显式不可用；配齐 → `/v1/health`
  报 `semantic_search: true`）。
4. **检索面的配置来源曾经是"venv 放在哪"的函数**（本轮真跑出来，主机上才复现）：`pymilvus.settings`
   在 **import 期**调用 `load_dotenv()`，python-dotenv 从 `pymilvus/settings.py` 所在目录**向上找
   `.env`**。宿主 venv 就在仓库根下（`<repo>/.venv/`），于是仓库 `.env` 被**顺手**写进
   `os.environ`——`serve` 的契约是"`--auth-token` 与 `SENSORYPLEX_INDEX_AUTH_TOKEN` 都缺失即
   拒绝启动"，而主机上 `--auth-token` 缺失时却拿到了 `.env` 里的令牌、照常起服务（容器里 venv 在
   `/app/.venv`，找不到，所以同一份代码在容器里是绿的）。修法是不给第三方 import 决定配置来源：
   新增 `sensoryplex_index_worker/environ.py`，在**任何会写 `os.environ` 的 import 之前**取一份
   `BASE_ENVIRON` 快照，`cli` 的令牌、`--uri` / `--database-url` / `--nats-url` 默认值与分级背压
   准入一律只读快照（准入通过 `read_event_backpressure(..., environ=BASE_ENVIRON)`）。`relay` 侧
   不动：它不 import `pymilvus`，进程环境本来就是干净的。契约测试
   `tests/contracts/test_index_environ_contract.py` 真造一次陷阱（cwd 放 `.env` + `python -c`，
  此时 dotenv 一定命中）并断言快照里没有它，把这条顺序约束钉住。

5. **`bare_settings` 只挡住了检索面三兄弟，没挡住那个唯一必填字段**（远端 CI 真跑出来的第 5 条）：
   `Settings.database_url` 是唯一的必填字段（无默认值），而 fixture 只 `delenv` 了
   `SENSORYPLEX_INDEX_SEARCH_*` 并传 `_env_file=None`——`database_url` **仍然由环境决定**。
   api 容器里 compose 注入了 `SENSORYPLEX_DATABASE_URL`，所以第 3 条新增的
   `test_blank_search_configuration_counts_as_unconfigured`（唯一一个没显式传 `database_url`
   的调用点）在本机与容器里全绿；CI 上既没有仓库 `.env`（未进检出）也没有这个变量，直接
   `ValidationError: database_url Field required`。这是第 1 条同一类病的残留：**只收口了用例
   想验的那几个变量，没收口"构造一个 `Settings` 到底需要什么"**。修法是让 fixture 自己收口：
   `delenv` 加上 `SENSORYPLEX_DATABASE_URL`，并 `setdefault("database_url", "postgresql://ignored/none")`
   （调用方仍可显式覆盖）。这样"忘了传"只会得到一个连不上的 `Settings`，不再是一台机器绿、
   另一台红。容器内摘掉该变量复现：修前 `362 passed, 1 failed`，修后 `363 passed`。

## 11. 一次差点走反的排查：同一份代码在主机与容器读到两套配置

这条**是真缺陷**（§10 第 4 条），但排查过程本身值得留档——容器里的反证一度把它判成了假象。

现象：`tools/verify_semantic_search.py` 场景 2（"没有令牌必须拒绝启动"）在**主机**上失败——
子进程拿到令牌、正常起服务、常驻到超时；而同一段代码在**容器**里是绿的。

机制（`pymilvus.settings` 在 import 期调用 `load_dotenv()`）：python-dotenv 从
`pymilvus/settings.py` 所在目录**向上找 `.env`**（`__main__` 没有 `__file__` 时退回用 cwd）。
于是"读不读得到仓库 `.env`"取决于 **venv 放在哪**：

| 运行位置 | venv 路径 | 向上能否走到仓库根 | 结果 |
| --- | --- | --- | --- |
| 主机（`make semantic-check`） | `<repo>/.venv/` | 能（venv 就在仓库根下） | **命中仓库 `.env`**，令牌被注入 |
| api / index 容器 | `/app/.venv`（仓库挂在 `/workspace`） | 不能 | 不命中，令牌保持缺失 |

容器里的那次反证之所以"成立"，是因为它在容器里跑——**布局本身被换掉了**，而"venv 放在哪"
恰恰就是这个缺陷的变量。同一次排查还推翻了另一条归因：`uv run` **不会**加载 `.env`（实测
`uv run --frozen python -c ...` 里 `SENSORYPLEX_INDEX_AUTH_TOKEN` 为 `None`，`pyproject.toml`
也没有 `env-file` 配置），所以锅不在 uv，在 pymilvus 的 import 副作用。

**教训（这类问题的通用形状）**：把"配置来源"交给第三方 import 的副作用，等于把配置来源交给
部署布局；而"在容器里验证"恰好会掩盖这类布局相关的缺陷——因为容器本身就是另一种布局。
验收要能同时覆盖两种布局，或者（更好）让代码不依赖布局。这里选后者。

## 12. 后果与仍未验证范围

**已落地**：`tools/macos_resident.py` 的 `event_queue_capacity` 与 `SENSORYPLEX_EVENT_QUEUE_CAPACITY`
渲染、`services/outbox-relay/src/sensoryplex_relay/residency.py`、relay 与 `serve --consume` 两侧的
准入与状态行、compose 的 `relay` / `index` 两个服务与 `deploy/up-events.sh` / `deploy/down-events.sh`、
`make events-up|events-down|events-logs`、`make event-pipeline-check`、契约测试与容器内验收脚本、
`services/index-worker/src/sensoryplex_index_worker/environ.py`（配置来源快照）与 `serve` 的 ready 行
改在消费确认之后写、
`tools/configure.py` 的检索面令牌。本切片**不加**数据库迁移。

**一条真实后果（本轮实测，不是缺陷）**：两个进程的**内置默认深度**在 `small` / `medium` 档都超标
——relay 的 `--batch` 默认 **200**、消费的 `--consume-batch` 默认 **50**，而这两档的上限是 16 / 32。
所以在注入了 `resident.env`（或 compose 里显式给了档位）的机器上**必须显式给值**：compose 给的是
`${SENSORYPLEX_EVENT_RELAY_BATCH:-16}` 与 `${SENSORYPLEX_EVENT_CONSUME_BATCH:-32}`。
这在容器里实测过：relay 容器（`medium` / 32）里裸跑 `--describe` 会得到
`event_inflight_exceeds_tier_cap: declared=200 tier_capacity=32 tier=medium`。这是**显式失败**而不是
静默超限——原来的"默认 200 照跑"现在会被一句话挡住。

**仍未验证（不得声称完成）：**

- **检索面停机时的降级路径**（`semantic_index_unreachable`）由
  `tests/integration/test_semantic_search.py` 覆盖，**不在**本切片的容器内闭环里；
- **服务端 Milvus 形态**（多进程拓扑）仍未验收——本机 Docker Hub 不可达（ADR-020 §6/§7），
  所以"消费与检索拆成两个进程"依然没有证据；
- **多副本消费**（同一个 durable 跑两个 index 进程）未验收：向量库是进程独占的，第二个进程预期会
  `vector_store_locked`，但这条路径没有被跑成场景；
- **跨主机 NATS 集群**未验收：compose 里的 nats 是单节点；
- **`ack_wait` 到期后的自动重投**仍未单独验收（验收走的是 nak 路径）；
- **macOS 常驻形态下的注入路径未接**：分级值确实渲染进了 `resident.env`
  （`tools/macos_resident.py render`，第四列就在里面），但 relay / index 在 macOS 上**还没有**
  launchd job，也没有包装脚本——`deploy/macos/bin/` 至今只有 `sensoryplex-media-run`，
  它 source 的是**媒体链路**那一份环境。所以 macOS 上要按分级跑事件链路，目前只能由调用方自己的
  环境提供这两个变量；"引擎按档自动注入"在 macOS 上**没有证据**（compose 路径是显式把值传进去的，
  那条有证据）。`launchd/org.sensoryplex.runtime.plist.template` 也**刻意不**带
  `SENSORYPLEX_EVENT_QUEUE_CAPACITY`：那个 job 跑的是 Rust `serve`，它不读事件链路的变量。
- **`golden_path_verified` 仍恒为 false**：真实媒体端到端（真实视频 → Runtime/Timeline → 事件）
  仍未联调，所以"真实素材被抽帧后自动产出向量并检索到"依然没有证据。
