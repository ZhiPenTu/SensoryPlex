# ADR-030：插件热部署执行器与蓝绿版本化实例（local_native 首期）

**状态：** Accepted（首期实现已落地；macOS 原生执行器已实机验收，Linux 平台服务适配器待 Linux 节点单独验收）<br>

**相关文档：** [开放插件开发文档](../../开放式插件开发文档.md)、[开发执行清单](../development-checklist.md)、[实现状态](../implementation-status.md)

## 1. 背景与目标

ADR-026 建立了"部署意图 + 状态上报"通路：控制面下发不可变 intent，Agent 领取后执行并回报。但 ADR-026
那一版的 Agent 只做**目录创建与状态标记**——它不解包受控归档、不校验可执行内容、不用平台服务托管进程、
不探测 endpoint、也不做版本切换。`make node-check` 场景 5 验收的是"意图通路 + 审计 + digest 回滚"，不是
真实热部署。把这条通路称为"插件已可热部署"是错误的能力声明。

本 ADR 把这条通路升级为**真实执行闭环**，范围被刻意收窄：

- **只支持 SensoryPlex 自研、`local_native`、macOS/Linux 的首方插件。**
- 热部署的定义是**独立进程的版本化蓝绿切换**：新版候选实例与旧版 active 实例并存，验证通过后切换
  active 指针，再排空并停止旧版。**不启用、也不承诺进程内 `hotReload`**——Python 进程内重载无法保证
  模型会话、数据面 lease 与 gRPC 服务的原子替换，承诺它就是承诺一个做不到的语义。

**显式不在范围内：** 容器形态插件、第三方未签名插件、意图内任意下载 URL、跨机共享内存、业务
`Process` 调用验证（GP-01 已由 ADR-028 覆盖）、自动 CPU fallback。

## 2. 决策

### 2.1 不可变 Release 是唯一可激活的身份

新增 `plugin_release`（不可变）。一个 release 记录：插件身份（`plugin_id`/`plugin_version`）、平台与架构
（`platform`/`arch`）、形态（本 ADR 仅 `local_native`）、**可执行内容摘要 `artifact_digest`**、
**完整传输内容摘要 `bundle_digest`**、manifest / config-schema / SBOM 三个子摘要、`bundle_bytes`、运行时
前置条件（Python 版本、入口、依赖锁定文件）与认证状态（`trust=first_party` + `authenticated`）。

- `artifact_digest` 沿用既有 `package_digest`（`pyproject.toml` + `src/`，见插件包 `artifact.py`），它是
  **插件可执行代码的身份**，也是候选进程启动时必须自证的值（`--expect-digest`）。
- `bundle_digest` 是**整包传输内容**的 sha256，即 `tar.gz` 文件本身的摘要。bundle 内部的
  `bundle.manifest.json` 逐文件声明 `sha256`/`bytes`/`mode`，因此 manifest 不需要、也不允许包含自身摘要，
  **自引用问题在格式层面被消除**。
- 只有 `trust=first_party AND authenticated` 的 release 可以被激活。`local_native` 插件在本版本**未签名**，
  所以"认证"的语义是：release 由受控制品仓（仓库内 `tools/plugin_release.py` 构建、落在 `.data/releases/`）
  产出，且 API 在**导入时重新计算落盘 bundle 字节的摘要**并与描述符比对。客户端无法通过提交 JSON 伪造摘要。

### 2.2 Bundle 是平台定向的受控归档

`plugin_release` 的 bundle 是平台+架构定向的 `tar.gz`，内容固定为：

```
bundle.manifest.json     # 格式版本、release 描述符、entrypoint、runtime 前置条件、逐文件摘要
payload/plugin.yaml      # manifest
payload/config.schema.json
payload/sbom.cdx.json
payload/pyproject.toml
payload/src/...          # 插件源码（可执行内容）
payload/requirements.lock.txt   # 锁定依赖（含 --hash）
payload/wheelhouse/*.whl        # 离线轮子（含 SDK 与全部运行时依赖）
```

Agent 解包前必须拒绝：绝对路径、`..` 逃逸、符号链接与硬链接、设备/FIFO 等特殊成员、超出单文件/总大小
上限的成员、manifest 未声明的成员、manifest 声明但缺失的成员，以及**任一文件摘要不匹配**。任一拒绝都是
稳定错误码 + 显式失败，不做"跳过该文件继续"。

**Agent 离线安装：不在部署时联网拉依赖。** 解包后创建私有虚拟环境并从 `wheelhouse/` 离线安装
（`--no-index --find-links` + `requirements.lock.txt` 的 `--hash`）。任何需要联网的安装都是失败，不降级。

### 2.3 逻辑槽位 + 版本化运行实例 + 部署操作

沿用 `console_plugin_instance` 作为 `(node_id, plugin_id)` 的**逻辑槽位**（它上面的唯一约束就是槽位语义），
追加两张表：

- `plugin_runtime_instance`：一个**版本化运行实例**（release + generation + role + state + endpoint +
  supervisor + unit 名 + 安装目录 + 验证后的插件身份 + 各阶段耗时）。同一槽位下允许 `candidate` 与
  `active` 并存——这是蓝绿的全部意义。
- `plugin_deployment_operation`：一次**部署操作**，持有阶段状态机、generation、deadline、目标 release、
  候选 runtime instance、`from` runtime instance、回滚来源 operation，以及各阶段耗时与错误码。

`console_plugin_instance` 追加 `active_runtime_instance_id` / `active_release_id` /
`previous_runtime_instance_id` / `generation` / `endpoint`：**槽位的 active 指针**由控制面以事务 +
generation CAS 切换，Scheduler 只解析 active endpoint。

### 2.4 操作状态机

```
accepted → staging → starting → validating → candidate_ready → cutting_over → draining_old → succeeded
```

- `accepted`/`cutting_over`/`draining_old`/`succeeded` 由控制面推进；`staging`/`starting`/`validating`/
  `candidate_ready` 由 Agent 回报推进。
- 失败进入 `failed` 并记录稳定错误码。**切换前失败（`accepted`→`candidate_ready` 任一阶段）旧 active 不变**，
  候选实例按显式失败清理，槽位 active 指针不动。
- **显式回滚创建反向部署操作**（`kind=rollback`、`rollback_of_operation_id` 指向原操作），不改写历史操作行。
- 取消只允许在 `cutting_over` 之前；`cutting_over` 之后拒绝取消并要求显式回滚。
- 回报给管理面的 `PluginDeploymentOperation.active` 是**读取时槽位的 active 指针**（切换成功后即本次
  候选实例，切换前失败则仍是本次操作开始前在服务的旧实例），本次被替换的实例只由
  `from_runtime_instance_id` 表达；历史操作行不被改写，两者语义不混用。

### 2.5 Agent 只按 release_id 取受认证制品

Agent 只接受控制面下发的 `release_id` + `bundle_digest` + `operation_id` + `generation` + `deadline`，
从**受认证下载端点**（`/v1/agent/releases/{release_id}/bundle`，要求携带与意图匹配的 Agent 会话令牌）
取 bundle。意图内**不接受任意 URL、命令、宿主路径或密钥**；入口命令来自 release 的 `entrypoint`，由
控制面从受控 manifest 推导，Agent 不解析未受控字段。

### 2.6 平台服务适配器：版本化实例由平台托管

- **macOS：** 用户级 LaunchAgent（`~/Library/LaunchAgents/<label>.plist`），
  `RunAtLoad` + `KeepAlive.SuccessfulExit=false`（**异常退出才重启**），`ProcessType=Background`，
  私有日志路径，受限环境变量白名单。
- **Linux：** systemd user unit（`~/.config/systemd/user/<unit>`），`Restart=on-failure`，
  `RestartSec` 有界，`PrivateTmp`/受限环境，日志走 journal。

两者都使用**版本化 unit 名**（含 release/generation），因此新旧两版可以同时存在；卸载 unit 只删该版本。

### 2.7 endpoint 文件契约（替代 stdout 推断）

Agent 以 `--port 0` 启动候选进程，由内核分配端口。插件完成绑定后**原子写出** loopback endpoint 文件
（`--endpoint-file <path>`，写临时文件再 `rename`）。Agent **不从非结构化 stdout 推断端口**：只轮询该文件，
超时即显式失败。四个首方插件都实现该契约。

### 2.8 候选验证序列

候选实例必须依次通过，才允许切换 active：

1. `Describe`（gRPC `ProcessorPluginService`）——拿到插件声明的身份；
2. 身份/摘要核对——`Describe` 的插件身份与 release 一致，进程自证的 `artifact_digest` 与 release 一致；
3. `ValidateConfig`；
4. `Start`（携带配置）；
5. **连续三次 `Health=ready`**。

默认启动总时限 **5 分钟**、健康间隔 **5 秒**；所有超时都是显式失败（`candidate_start_timeout`、
`candidate_health_timeout` 等），不夹取、不重试到成功为止。

### 2.9 蓝绿预检与资源余量

切换前按**旧实例声明的资源 + 候选资源**计算升级余量。不足时返回 `upgrade_headroom_insufficient`：
**不停止旧版本、不隐式降级为停机更新**。余量按节点心跳上报的可用内存与槽位内已声明资源计算。

### 2.10 切换、排空与回滚制品保留

控制面在事务内以 generation CAS 切换槽位 active 指针与 endpoint；随后对旧实例下发 `Drain`（停止新任务），
等待**不短于插件 `defaultDeadlineMs`** 的受限 grace period，再 `Stop` 并卸载 unit。旧 bundle **留在盘上**
作为已验证的回滚版本，不删除。

### 2.11 Agent 重启对账

Agent 重启时按平台服务的**实际状态**、endpoint 文件与控制面 generation 对账，并通过心跳里的
`runtime_observations` 上报。未知状态**不猜测成功、不删除 active/previous 制品**，只报告
`reconciliation_required`。

### 2.12 管理面与可观测性

- Console 插件中心：可选**已认证 release**、升级确认、实时阶段/错误码、当前与上一版本、显式回滚，
  以及下载/启动/排空耗时。
- API：部署创建、操作详情、取消（仅切换前）、回滚；release 下载仅向持有匹配意图的 Agent 会话开放。
- 指标：`GET /admin/v1/plugin-deployments/metrics` 对部署台账做真实 `GROUP BY`，按
  `node/plugin/release/kind/stage/reason` 输出 Prometheus exposition（操作计数 + 各阶段耗时 sum/max；
  `kind` 区分 provision / upgrade / rollback，让"按操作聚合"不把升级与回滚混成一桶）。
  `operation_id` **故意不进 label**（高基数，见 `docs/design/plugin-orchestration.md` §8），逐操作耗时
  由操作资源与审计行承担；窗口内没有台账就没有 series，**不合成、不补零**。抓取链路（独立指标服务或
  scrape 配置）不在本 ADR 范围内。
- 所有写操作使用 `plugins:manage`；只读状态遵从既有节点权限。
- 日志、审计与指标按 `node/plugin/release/operation/reason` 聚合；**不记录** bundle 内容、命令行密钥、
  配置秘密、原始媒体或模型输入。

## 3. 后果

- `golden_path_verified=false` **不变**：本 ADR 是部署面能力，不是业务闭环。
- 文档状态必须区分三档：**部署意图通路**（ADR-026，已验收）、**真实热部署执行器**（本 ADR，macOS 首方
  插件实机验收后可称"已实现"）、**跨平台/第三方**（未验收）。Linux 平台服务适配器在 Linux 节点单独验收
  之前**不得宣称支持**。
- 失败语义全部显式：摘要不符、路径逃逸、非首方 release、重复投递、陈旧 generation、资源不足、候选启动
  失败、配置校验失败、排空超时、对账未知——各有稳定错误码，不静默 fallback。
