# ADR-009：媒体格式支持矩阵与显式拒绝语义

**状态：** Accepted（2026-09-23）
**上游决策：** ADR-003（实时媒体用 GStreamer、离线工具用 FFmpeg）、ADR-008（Apple Silicon 是一等端侧目标）
**相关文档：** [技术选型 ADR 与 V1 实施蓝图](../../技术选型ADR与V1实施蓝图.md)、[实现状态](../implementation-status.md)、[验证记录](../verification.md)、[待办](../TODO.md)

## 1. 背景与问题

基座已经能在真实样本上跑通"解码 → arena → `BufferDescriptor` → lease → 音频切段"
（HEVC/AAC MP4 与一批 VP9/Opus WebM 样本，后扩充到 10 个公开许可样本，证据见 [验证记录](../verification.md) 与 `tests/fixtures/media/OPEN-SAMPLES.md`）。
但**准入判据是缺失的**，这带来三类已经实测到的静默降级，都属于 AGENTS.md 明令禁止的行为。

**实测 A：10-bit 源被静默降成 8-bit，且报告里没有任何字段记录这件事。**

```console
$ ffprobe -show_entries stream=codec_name,profile,pix_fmt -of csv=p=0 /tmp/p10.mp4
hevc,Main 10,yuv420p10le

$ GST_DEBUG=GST_ELEMENT_FACTORY:4 gst-launch-1.0 -v filesrc location=/tmp/p10.mp4 \
    ! decodebin ! videoconvert ! 'video/x-raw,format=RGBA' ! fakesink sync=false
creating element "h265parse"
creating element "vtdec_hw"
... video/x-raw(memory:GLMemory), format=(string)NV12 ...
... video/x-raw, format=(string)RGBA ...
```

下游 capsfilter 只写了 `format=RGBA`，没有位深约束，于是 `videoconvert` 接受任何输入格式：
源是 Main10，产物是 8-bit，整条链路**成功退出**。`DecodedTrackStat.pixel_format` 只会写 `RGBA`，
调用方无法区分"源就是 8-bit"和"源是 10-bit 被降位了"。

**实测 B：无法识别的 pad 只写日志，不进入任何报告。**

`crates/media/src/decode.rs` 的 `classify()` 只看 caps 主类型前缀（`video/`、`audio/`），
其余分支走 `tracing::warn!("decoded pad ignored: unsupported media type")`。
日志不是契约：`ReplayReport.blockers` 与 `DecodedTrackStat.drop_reasons` 都不会出现这一条，
报告读起来像"这个文件没有视频轨"，而不是"这个文件有视频轨但被拒绝了"。

**实测 C：多声道被原样透传。**

音频链 capsfilter 只约束 `format=F32LE`，不约束声道数：

```console
$ gst-launch-1.0 -v filesrc location=/tmp/s51.mp4 ! decodebin ! audioconvert \
    ! 'audio/x-raw,format=F32LE' ! fakesink sync=false
audio/x-raw, format=(string)F32LE, rate=(int)48000, channels=(int)6
```

5.1 AAC 源以 6 声道进入数据平面。这不是"错误"，但 v1 的 ASR 路径按 mono/stereo 设计，
多声道属于**未承诺、也未声明不支持**的中间地带。

**用户决策：** 先只支持主流格式，随后逐个添加；允许引入现成库解决覆盖问题。
本 ADR 就是把"主流"写成一张可验收的白名单，并把白名单之外的行为全部定义成显式拒绝。

## 2. 决策一：V1 承诺矩阵（白名单）

**只承诺下表中的组合；表外一律拒绝（§3），不得静默处理。**

矩阵是"承诺清单"，**不等于"已有证据清单"**：目前有真实回放证据的是 MP4/MOV（HEVC/AAC 与
H.264/AAC）、MKV/WebM（VP9/Opus 与 VP8/Vorbis）、MPEG-TS（文件形态 H.264/AAC 与 SRT 直播形态），
以及容器内 PCM（MOV 里的 `pcm_s16le`）；矩阵里其余行在补上样本之前不得对外声称可用。
**矩阵外组合的拒绝语义已实现并实测**（2026-09-23，`make capability-check` 19 场景，
见 [验证记录](../verification.md) 的"M9"一节），因此 §3 的拒绝码不再只是约定。
图例：✅ 已有回放证据 ｜ 🔒 已实现显式拒绝（有实测拒绝记录）｜ ⏳ 无证据（无批准不得声称可用）｜
❌ 当前行为与决策冲突，待修

> §2 的表里当前**没有一行还标 ⏳**：原先缺真实回放样本的 H.264、VP8、Vorbis、容器内 PCM 与
> 文件形态 MPEG-TS 已于 2026-09-23 补齐（样本见 `tests/fixtures/media/OPEN-SAMPLES.md`）。

### 2.1 容器

| 容器 | demuxer 元素（实测存在） | V1 状态 | 证据 |
|---|---|---|---|
| MP4 / MOV | `qtdemux` | 承诺 | ✅ `video/1.mp4`（HEVC/AAC） |
| MKV / WebM | `matroskademux` | 承诺 | ✅ 6 个 VP9/Opus 样本 |
| MPEG-TS | `tsdemux`（所属插件 `mpegtsdemux`） | 承诺（SRT 直播的承载容器） | ✅ SRT 直播形态实测（`make live-check` 5 场景，`steady` 下 video/audio 均未被拒）+ **文件形态**样本 `mpegts-h264-aac.live-recording.ts`（H.264/AAC，`rejected=0`） |
| AVI / FLV / OGG / WAV / FLAC / RTP / 裸 ES 等 | — | 显式拒绝 | 🔒 `unsupported_container_avi`、`unsupported_container_raw_es`（裸 H.265 ES）、`unsupported_container_ogg`（Vorbis 装进 Ogg）、`unsupported_container_wav`（PCM 装进 WAV）实测；**有容器头**的音频容器（WAV/FLAC）与裸 ES 分开命名，不再被误读成裸 ES；FLV/RTP 走同一条通用码路径，未实测 |

### 2.2 视频

| 编码 | 位深 / 传输特性 | V1 状态 | 证据 |

| HEVC | 8-bit SDR（Main） | 承诺 | ✅ `video/1.mp4`，macOS 由 `vtdec_hw` 解出 |
| VP9 | 8-bit SDR（Profile 0） | 承诺 | ✅ 样本矩阵主力格式 |
| VP8 | 8-bit SDR | 承诺 | ✅ `editing-basics-sandboxes.vp8.webm`（`vp8dec0`）；`video/x-vp8` caps **不含** profile/位深/采样格式，报告里的 8 与 `4:2:0` 是矩阵对 Profile 0 的推导（见 §10） |
| AV1 | 8-bit SDR | 实验 | 🔒 按矩阵外处理（`unsupported_codec_av1`）；仅 `av1dec` 存在性实测，不进 Golden Path，不作验收阻塞项 |

| ProRes / DNxHD / MPEG-2 / VC-1 / JPEG2000 | — | 显式拒绝 | 🔒 通用编码拒绝路径（`unsupported_codec_prores` 有单测）；无真实样本 |

### 2.3 音频

| 编码 / 布局 | V1 状态 | 证据 |
|---|---|---|
| AAC-LC | 承诺 | ✅ `video/1.mp4` |
| Opus | 承诺 | ✅ VP9 样本；pre-skip 差异已按轨道容差校准 |
| Vorbis | 承诺 | ✅ `editing-basics-sandboxes.vp8.webm`（`vorbisdec0`，44.1 kHz stereo） |
| 容器内 PCM | 承诺 | ✅ `conger-conger.h264-pcm.mov`（`pcm_s16le` 48 kHz stereo；无解码器，报告写 `demuxer_passthrough`） |
| AC-3 / E-AC-3 / DTS / TrueHD | 显式拒绝 | 🔒 通用编码拒绝路径；AC-3 已在 MPEG-TS 里实测（`unsupported_codec_ac3`，同流 video 照常解码）；E-AC-3 / DTS / TrueHD 无实测样本 |
| `channels > 2` | 显式拒绝（v1 只承诺 mono/stereo） | 🔒 实测 C 已修：`unsupported_channel_layout_multichannel`（`make capability-check`）；相邻的 `unsupported_codec_mp3`（mpegversion 区分）亦实测 |

### 2.4 归一化目标（不随输入格式变化）

| 平面 | 目标 caps | 元素 |
|---|---|---|
| 视频 | `video/x-raw,format=RGBA` | `videoconvert` |
| 音频 | `audio/x-raw,format=F32LE` | `audioconvert` |

归一化目标保持不变；变化的是**在归一化之前先做准入判定**，而不是让 `videoconvert` 兜住一切。

**归一化链必须接住硬解给出的 GLMemory。** 实测（2026-09-23）：同一进程里出现第二个 VideoToolbox
解码实例时，`vtdec_hw` 会**偶尔**按 `video/x-raw(memory:GLMemory)` 协商输出（`vtdec_hw` 的 src
模板把 GLMemory 排在首位），而 `videoconvert` 不接受 GLMemory，表现为 `pipeline_state_change_failed`
或 `decode_stalled` 这类**与格式无关的随机失败**。修法是在视频链的 `queue` 与 `videoconvert` 之间
插入 `gldownload`：它的 sink 同时接受 GLMemory 与系统内存、src 只输出系统内存，把"硬解后端给什么"
与"归一化目标"解耦；元素缺失时退回原链路（见 §9）。

## 3. 决策二：白名单之外一律显式拒绝

**规则：** 任何不在 §2 矩阵内的 `(container, codec, bit_depth, chroma, channel_layout, transfer)` 组合，
必须在 caps 协商阶段被判定为拒绝，并且**同时**满足：

1. 拒绝码进入 `ReplayReport.blockers`（该构建整体不支持）或
   `DecodedTrackStat.drop_reasons` / `decoded.failure_reasons`（该流不支持）**二者之一**；
2. 拒绝码是稳定字符串，不写自由文本，不复用 `unsupported_media_source` 这类宽泛错误；
3. 该轨道不得产生 `BufferDescriptor`，也不得让计数看起来像"流里本来就没有这条轨道"；
4. 禁止"只写日志"——`tracing::warn!` 是运维信息，不是契约（实测 B 的修法）；
5. 禁止降级成功——不接受"先降到 8-bit 再报成功"（实测 A 的修法）。

**拒绝码命名规范**（`unsupported_` 前缀 + 维度 + 取值）：

| 维度 | 示例 |
|---|---|
| 容器 | `unsupported_container_avi`；有容器头的音频容器单独命名（`unsupported_container_wav` / `unsupported_container_flac`），不并入 `unsupported_container_raw_es` |
| 编码 | `unsupported_codec_prores` |
| 位深 | `unsupported_bit_depth_10bit` |
| 色彩/传输特性 | `unsupported_transfer_characteristics_pq` |
| 声道布局 | `unsupported_channel_layout_multichannel` |
| 轨道结构 | `unsupported_track_layout_multiple_video` |
| 时间基准 | `unknown_timing_base`（对应 `MediaTrack.timing_known=false`） |

## 4. 决策三：采集源格式上下文，在 caps 协商阶段完成准入

新增 `crates/media/src/capability.rs`，把矩阵写成数据而不是散落的 `if`。
分类输入必须同时包含**按轨道关联的源格式上下文**和解码后的格式，不能只传一份 raw caps：

```text
SourceFormatContext { track_id, container, codec, profile, bit_depth, chroma, channel_layout, transfer }
DecodedFormat { pixel_format, width, height, sample_rate, channels }
classify_format(&SourceFormatContext, &DecodedFormat) -> Verdict::{Admitted, Rejected { code, detail } }
```

以上是 Rust 内部设计草案，不是新增跨进程消息；对外字段仍以 `proto/` 为唯一来源。
源字段取不到时保持未知，不能从归一化后的 `pixel_format` 反推源位深或用默认值补齐。

**信息采集与关联：**

1. 在 typefind / demux 阶段记录容器类型；它不属于解码后的视频或音频 caps。
2. 在 demux 输出、parser 输出或 `decodebin` 的 autoplug 阶段采集编码、profile、源位深与色彩信息。
   应保存送入解码器的已解析 caps；若信息来自容器元数据或 tag，也必须记录来源。
   **demuxer 的 src pad 必须单独挂探针**：`deep-element-added` 的 sink 探针只在元素内部链路上
   协商时触发，而容器里**直存 raw 采样**的轨道（MOV 里的 `pcm_s16le`）没有 parser/decoder，
   那条路径永远等不到 caps——实测后果是 PCM 轨被误拒成 `unknown_source_codec`。而且 demuxer 的
   src pad 是**解析时**才创建的，接线阶段的 `iterate_src_pads()` 拿不到它，必须在 `pad-added`
   回调里补挂（实测要求，不是调参）。
3. 用 GStreamer 的轨道标识（STREAM_START 的 stream ID）及 pad 上下游关系，将这些信息关联到
   `decodebin` 的输出 pad。这里的 `track_id` 是单条轨道标识，区别于业务 `stream_id`；
   禁止按 pad 出现顺序或仅按 video/audio 类型配对，以免多轨信息串用。
4. `pad-added` 负责关联并安装输出侧检查；结合 CAPS event 校验解码后的格式，
   在向归一化链放行 buffer 前完成准入。该回调暴露的通常已是 `video/x-raw` / `audio/x-raw`，
   不能把它当作解码器输入 caps。

**约束：**

- 一旦源上下文已能确定不支持，就立即记录拒绝，不必等待解码后的 pad；缺少解码器而触发的
  `unknown-type` / missing-plugin 路径也必须进入报告，不能只依赖 `pad-added` 统计失败。
- Main10 即使被硬解输出为 NV12，也仍按源侧信息拒绝（实测 A）；raw caps 只能描述当前载荷。
- 准入所需的源信息缺失或无法关联时，不得放行；等待信息受已有 timeout 与队列上限约束，
  到期以稳定原因码（如 `unknown_source_bit_depth`、`source_track_unresolved`）拒绝并上报。
  已准入轨道后续发生 CAPS 变化时，必须更新上下文并重新判定，不能沿用首次结论。
- 现有 `classify()` 的 `Option<TrackKind>` 返回值不足以表达拒绝原因，需要同时返回
  可选的 `TrackKind` 与 `Verdict`；非音视频 pad 也要落到显式计数上，不能虚构轨道类型。
- 复用既有机制，不新造平行体系：进程级缺失进 `blockers`，
  流级拒绝进 `drop_reasons` / `failure_reasons`，与 `unavailable_reason` 的语义保持一致。
- **被拒绝的 pad 也必须有 peer。** "在链头丢弃样本"只对已连接的链路有效：一条 pad 若只被 `return`
  而不链接任何元素，在上游看来就是"没接上"（`not-linked`），会让**相邻轨道**的解码随机失败。
  被拒 pad 必须显式终结到 `fakesink(sync=false, async=false)` 上；该 sink 不指定 `name`
  （曾用固定名导致第二条被拒轨道报 "not unique in bin"）。

**验收方式（每个拒绝项一条负样本）：** 负样本可以合法地用 FFmpeg 合成
（如 `-pix_fmt yuv420p10le` 造 10-bit、`-af pan=5.1` 造多声道），
但必须在报告里标注为"拒绝路径验证样本"，**不得**作为任何正样本证据。
另须验证源上下文的关联：相同 raw caps 来自白名单内外源格式时，准入结果仍应由源信息决定；
多轨、缺失源信息与 CAPS 变化不得绕过拒绝或造成轨道信息串用。

## 5. 决策四：解码主路径唯一，FFmpeg 只做探测与离线基线

**决策：** GStreamer 是唯一解码主路径，不变（ADR-003）。
需要额外格式覆盖时，**优先使用已安装的 `gst-libav`（`libav`）元素**，
不引入 `rsmpeg` / `ffmpeg-next` 这类第二套解码器。

**理由：** 现有的时间戳语义是按 GStreamer buffer 校准出来的——Opus pre-skip、
毫秒粒度的段边界回退、容器 edit list 的呈现原点。再引入一套解码器就是再引入一套 PTS 语义，
两套语义会在 descriptor 与 report 层互相污染，而且很难用测试证明"等价"。

**解码器选择必须可追溯。** `decodebin` 自动协商，实际选中哪个元素随平台变化，实测（2026-09-23，`macos-aarch64`）：

```console
$ GST_DEBUG=GST_ELEMENT_FACTORY:4 gst-launch-1.0 -q \
    filesrc location=video/1.mp4 ! decodebin ! fakesink sync=false
creating element "h265parse"
creating element "vtdec_hw"      # HEVC 走 VideoToolbox
creating element "avdec_aac"     # AAC 走 gst-libav
```

同一台机器上 `gst-inspect-1.0 avdec_hevc` **不存在**。也就是说：
macOS 的 HEVC 覆盖来自 VideoToolbox 而不是 libav；Linux 侧是否有 `avdec_hevc` /
`nvdec` / `nvv4l2decoder` 必须**逐主机实测**，不能从 macOS 结论外推
（ADR-008 的"跨平台结论必须标注平台与执行后端"）。

**因此：** 解码器元素名（如 `vtdec_hw`、`avdec_h264`）必须进入报告证据，
否则"这个格式在 macOS 上可用"这句话无法被复核。

**许可提醒（部署检查清单项）：** 本机 FFmpeg 是 `--enable-gpl` 构建
（实测 `ffmpeg 9.0.1 ... --enable-gpl ... --enable-libx264 --enable-libx265`）。
GPL 组件不得进入分发产物；`gst-libav` 同样受其底层 `libav*` 构建的许可约束。
发布产物必须验证 `ffmpeg -version` 的 `configuration` 行，而不是假定发行版默认值。

**可选纯 Rust 后端（评估结论，暂不引入）：** Symphonia 只覆盖音频解码，且同样会引入第二套
时间戳语义；若将来引入，只能作为**可选后端**并复用同一 descriptor/report 契约。
`audiobuffersplit`（实测存在）可以先不替换手写 segmenter——现有切段已有段边界证据，
替换属于 `docs/TODO.md` 第 3 节的优化项，不属于格式支持范围。

## 6. 决策五：两个契约缺口现在钉死

矩阵一旦承诺"8-bit SDR、单一视频轨"，就必须能**表达**违反它的输入，否则拒绝无从判定。
当前 `proto/common/v1/common.proto` 的 `BufferFormat` 只有
`pixel_format / width / height / strides / sample_rate / channels`，缺两组字段：

**(1) 几何：** `display_rotation_deg`、`pixel_aspect_ratio_num/den`。
手机竖屏素材与 anamorphic 素材现在会被当成"几何正确"处理，错误会一路传导到 OCR/VLM 输入。

**(2) 位深与色彩：** `bit_depth`、`color_primaries`、`transfer_characteristics`、`matrix_coefficients`。
没有这四个字段，实测 A 的降位就无法被表达，只能继续"看起来成功"。

**Proto 归属（待实现）：**

| 文件 / 消息 | 需要补充的内容 |
|---|---|
| `proto/common/v1/common.proto` / `BufferFormat` | 本节两组字段，使模型插件收到的 `BufferDescriptor.format` 能携带几何与源位深/色彩信息 |
| `proto/media/v1/media.proto` / `MediaSourceDescription`、`MediaTrack` | 容器、轨道标识、源格式信息，以及 §7 的时间基与帧率模式；被拒轨道的源信息也必须保留 |
| `proto/media/v1/media.proto` / `DecodedTrackStat` | 与源轨道的关联、实际应用的旋转角度、§5 的解码器元素证据及拒绝原因 |

这些字段不能只加在回放报告中；插件读取的是 `common.proto` 定义的 descriptor。
被拒轨道通过源信息和报告表达，不为填充字段而创建 `BufferDescriptor`。
新增字段必须保留未知语义，使用 optional 或带 UNKNOWN 的枚举，不能用缺省的 0 冒充已知值。

配套规则：

- v1 只承诺 `display_rotation_deg ∈ {0, 90, 180, 270}` 且 SAR 为 1:1 或可显式上报；
  其他取值显式拒绝。
- 旋转必须在归一化阶段真正应用（`videoflip` 实测存在），并且报告中记录应用过的角度——
  下游模型拿到的帧必须是"呈现后"的画面，而不是未旋转的原始帧。
- `bit_depth` 记录**源**位深；`unsupported_bit_depth_*` 拒绝码记录被拒的那一位。
  两者都不是估算值，取不到就按"未知"表达，不得填默认值。

---

## 7. 决策六：时间基与帧率模式显式化

现有 `MediaTrack.timing_known` 只能表达"知道 / 不知道"，`DecodedTrackStat.timeline_offset_ms`
只覆盖 edit list 原点。需要补两项：

- **时间基：** `timescale_num/den`（容器声明的刻度），使 `pts_ms` 的取整来源可复核。
- **帧率模式：** `CONSTANT | VARIABLE | UNKNOWN`。现有 6 个样本**全部是 CFR**
  （见 [待办](../TODO.md) 待补样本），v1 不承诺 VFR 抽帧语义；
  但 v1 必须能**声明**一条轨道是 VFR 或 UNKNOWN，禁止把未知帧率当 CFR 处理。

`timing_known=false` 的轨道不得进入 timeline fusion（`media.proto` 注释已规定），
这一点在接入 VFR 前保持有效。

---

## 8. 决策七：新增一个格式的固定成本

增加一个格式 = 下面四件事，缺一件就不算支持：

1. `capability.rs` 矩阵加一行（含拒绝码的另一半）；
2. 一个**正样本**：真实授权素材跑通回放，进 `tests/fixtures/media/OPEN-SAMPLES.md` 或等效记录；
3. 一个**负样本**：验证相邻的拒绝码确实触发（合成素材允许，只用于拒绝路径）；
4. `docs/verification.md` 一条证据行（平台标识、解码器元素、计数自洽性）。

这条规则的作用是让"支持格式"与"有证据"永远等长，避免矩阵变成愿望清单。

---

## 9. 后果与最小实现清单

按顺序落地（每一步都能单独验收）。**第 1–4 步已于 2026-09-23 完成**，
证据见 [验证记录](../verification.md) 的"M9"一节与 `make capability-check`：

1. ✅ Proto：`common/v1/common.proto` 的 `BufferFormat` 补了几何与源位深/色彩字段；
   `media/v1/media.proto` 补了源格式上下文、`RejectedTrack`、解码器元素、帧率模式与声明的帧率，
   `make proto` 已重跑。迁移语义保持只追加字段、不重编号、不改既有含义。
2. ✅ 按 §4 采集并关联源格式上下文，打通 `capability.rs`（矩阵 + `classify_track`）与拒绝上报路径；
   除 10-bit、多声道、未知 pad 三条相邻拒绝项外，还实测了 4:2:2、MP3、AVI、裸 ES、双视频轨与字幕 pad。
3. ✅ 实际选中的解码器元素（`vtdechw0`、`avdec_aac0`、`opusdec0`）进入报告证据。
4. ✅ 负样本（FFmpeg 现场合成/重封装，只用于拒绝路径）+ `docs/verification.md` 的"M9"一节；
   `docs/implementation-status.md`、`docs/contracts/README.md` 与 `docs/TODO.md` 已同步。
5. 🔶 按矩阵逐行添加格式（每行四件事，§8）：H.264、VP8、Vorbis、容器内 PCM 与文件形态 MPEG-TS
   五行已补齐（正样本 + 相邻负样本 + 验证记录，见 [验证记录](../verification.md) 的"M9"一节与
   `tests/fixtures/media/OPEN-SAMPLES.md`）；矩阵里其余行仍未开始。

**落地过程中暴露并修掉的两个缺陷**（写进决策，避免下次重犯）：

- `typefind ! decodebin` **直连**会让容器证据同时失效（`have-type` 不触发、demuxer 的 sink caps 未协商），
  容器永远未知 → 每条轨道都被 `unknown_source_container` 拒绝。typefind 与 decodebin 之间必须隔一条
  有界 `queue`（实测的接线要求，不是调参）。
- "源里没有这种轨道"不能读成"卡住"：pad 还没出现的链路不算活跃轨道，一条轨道都没出现时要有界等待后
  返回 `no_decodable_track: <容器结论/已记录拒绝>`，而不是耗尽 idle 预算报 `decode_stalled`。

**补样本过程中又暴露并修掉三个缺陷**（同样写进决策）：

- **多视频轨竞态**：双视频轨场景随机失败（HEVC 报 `pipeline_state_change_failed`，VP9/软件解码报
  `decode_stalled`）。根因是两件事叠加——被拒 pad 悬空（`not-linked`，见 §4）与 `vtdec_hw` 偶发
  按 GLMemory 协商输出（见 §2.4）。两处修复缺一不可；A/B 实测：单轨（`1.mp4`、`sintel`）0 失败；
  `two-video-h264.mp4` 修复前 4/10、修复后 0/10，`two-video.mp4`（HEVC）6~7/10 → 0/10，
  `two-video-vp9.mkv` 10/10 → 0/10（移除 `gldownload` 后分别回到 2/10、5/10、9/10）。
- **容器里直存 raw 采样的源编码采集不到**：PCM 轨被拒 `unknown_source_codec:
  codec_caps_not_collected`。修法是给 demuxer 的 src pad 在 `pad-added` 里补挂探针（见 §4），
  并把"没有解码器"钉成显式取值 `demuxer_passthrough`（`capability::NO_DECODER_ELEMENT`）——
  空串的含义仍然只是"本次运行没能归因到解码器"。该语义写进 `media.proto` 的
  `decoder_element = 17` 注释（`make proto` 已重跑）。
- **`audio/x-wav` / `audio/x-flac` 被误读成裸 ES**：这两个 caps 在容器表里本来就有短名
  （`wav`/`flac`），却先在裸 ES 表里命中，于是报出 `unsupported_container_raw_es` 而不是
  `unsupported_container_wav`。修法是把它们移出裸 ES 表（它们**有容器头**），并补两条命名断言。

**仍然成立的三条约束：**

- 不得对外声称任何矩阵外格式"可用"，也不得声称矩阵内**还没有回放证据**的行可用；标 🔒 的行
  只证明**拒绝路径**正确，不证明该编码在别的机器上"不能用"。
- `ReplayReport.golden_path_verified` 保持 `false`。
- `blockers` 只列当前构建仍然缺失的能力（例如 `lease_consumer_not_implemented`）；
  媒体准入的拒绝是**流级事实**（`DecodedDataPlane.rejected_tracks`），不进 `blockers`。
  摘除任何一条 blocker 都必须有对应的真实验收记录；禁止用"已计划"或"部分实现"来摘除。

## 10. 未验证范围

- 本 ADR 的实测结论均在 `macos-aarch64`（GStreamer 1.28.7、FFmpeg 9.0.1）取得；
  Linux/NVIDIA 侧的解码器可用性、以及 §9 里那条"typefind 必须隔一条 queue"的接线结论都未验证，
  不得外推（ADR-008：跨平台结论必须标注平台与执行后端）。
- **拒绝路径的证据来自 FFmpeg 现场合成/重封装素材**（10-bit、4:2:2、5.1、MP3、AVI、裸 ES、字幕、
  双视频轨）。它们只证明"这些输入会被显式拒绝"，**不**证明对应的真实采集素材也能被正确分类，
  也不构成任何格式可用性证据。
- H.264、VP8、Vorbis、容器内 PCM 与文件形态 MPEG-TS 已于 2026-09-23 补上真实回放样本
  （`make capability-check` 的 6 个正样本）。仍未覆盖：E-AC-3 / DTS / TrueHD 无实测样本
  （AC-3 已在 MPEG-TS 里实测）；HDR 只有合成 10-bit 的相邻证据，无真实 PQ/HLG 素材。
  标 🔒 的行只有拒绝记录。
- **VP8 的位深与采样格式是推导值**：GStreamer 1.28.7 的 `video/x-vp8` caps 不含 `profile` /
  `bit-depth-luma` / `chroma-format`，报告里的 `8` 与 `4:2:0` 来自矩阵对 VP8 Profile 0 的推导，
  证据强度低于 H.264/HEVC 的真读值，不得写成"源声明"。
- **文件形态 MPEG-TS 样本是本机 SRT 直推的重编码产物**（H.264/AAC），只覆盖文件路径的准入与
  回放；设备直出仍未验证，也不能替代 `make live-check` 的直播证据。
- **旋转（几何）未实现**：本机实测 `qtdemux` 对 `rotate=90` / DisplayMatrix 不暴露旋转信息，
  因此 `display_rotation_deg` 与 `applied_rotation_deg` 保持缺省（不填 0 冒充"未旋转"），
  手机竖屏素材的几何正确性未验证。
- CAPS 变化重判与"相同 raw caps 来自不同源格式"只有单元测试级证据，没有端到端样本；
  源信息缺失的**有界等待**目前只覆盖"源里一条轨道都没出现"的文件路径（2 秒）。
- 回放样本里除 `editing-basics-sandboxes.vp8.webm`（容器未声明帧率 → `UNKNOWN`）外都是 CFR；
  **容器级 VFR 长间隙**与**设备直出**仍无样本（见 [待办](../TODO.md) 待补样本）；
  VFR 抽帧语义本 ADR 不承诺。
- `golden_path_verified` 恒为 `false`；本 ADR 不改变这一点。
