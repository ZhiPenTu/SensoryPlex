# ADR-009：媒体格式支持矩阵与显式拒绝语义

**状态：** Accepted（2026-09-23）
**上游决策：** ADR-003（实时媒体用 GStreamer、离线工具用 FFmpeg）、ADR-008（Apple Silicon 是一等端侧目标）
**相关文档：** [技术选型 ADR 与 V1 实施蓝图](../../技术选型ADR与V1实施蓝图.md)、[实现状态](../implementation-status.md)、[验证记录](../verification.md)、[待办](../TODO.md)

---

## 1. 背景与问题

基座已经能在真实样本上跑通"解码 → arena → `BufferDescriptor` → lease → 音频切段"
（HEVC/AAC MP4 与 6 个 VP9/Opus WebM 样本，证据见 [验证记录](../verification.md)）。
但**准入判据是缺失的**，这带来三类已经实测到的静默降级，都属于 AGENTS.md 明令禁止的行为。

**实测 A：10-bit 源被静默降成 8-bit，且报告里没有任何字段记录这件事。**

```console
$ ffprobe -show_entries stream=codec_name,profile,pix_fmt -of csv=p=0 /tmp/p10.mp4
hevc,Main 10,yuv420p10le

$ GST_DEBUG=GST_ELEMENT_FACTORY:4 gst-launch-1.0 -v filesrc location=/tmp/p10.mp4 \
    ! decodebin ! videoconvert ! 'video/x-raw,format=RGBA' ! fakesink sync=false
creating element "h265parse"
creating element "vtdec_hw"
... video/x-raw(memory:GLMemory), format=(string)NV12 ...
... video/x-raw, format=(string)RGBA ...
```

下游 capsfilter 只写了 `format=RGBA`，没有位深约束，于是 `videoconvert` 接受任何输入格式：
源是 Main10，产物是 8-bit，整条链路**成功退出**。`DecodedTrackStat.pixel_format` 只会写 `RGBA`，
调用方无法区分"源就是 8-bit"和"源是 10-bit 被降位了"。

**实测 B：无法识别的 pad 只写日志，不进入任何报告。**

`crates/media/src/decode.rs` 的 `classify()` 只看 caps 主类型前缀（`video/`、`audio/`），
其余分支走 `tracing::warn!("decoded pad ignored: unsupported media type")`。
日志不是契约：`ReplayReport.blockers` 与 `DecodedTrackStat.drop_reasons` 都不会出现这一条，
报告读起来像"这个文件没有视频轨"，而不是"这个文件有视频轨但被拒绝了"。

**实测 C：多声道被原样透传。**

音频链 capsfilter 只约束 `format=F32LE`，不约束声道数：

```console
$ gst-launch-1.0 -v filesrc location=/tmp/s51.mp4 ! decodebin ! audioconvert \
    ! 'audio/x-raw,format=F32LE' ! fakesink sync=false
audio/x-raw, format=(string)F32LE, rate=(int)48000, channels=(int)6
```

5.1 AAC 源以 6 声道进入数据平面。这不是"错误"，但 v1 的 ASR 路径按 mono/stereo 设计，
多声道属于**未承诺、也未声明不支持**的中间地带。

**用户决策：** 先只支持主流格式，随后逐个添加；允许引入现成库解决覆盖问题。
本 ADR 就是把"主流"写成一张可验收的白名单，并把白名单之外的行为全部定义成显式拒绝。

## 2. 决策一：V1 承诺矩阵（白名单）

**只承诺下表中的组合；表外一律拒绝（§3），不得静默处理。**

矩阵是"承诺清单"，**不等于"已有证据清单"**：目前只有 MP4/MOV（HEVC/AAC）与 MKV/WebM（VP9/Opus）
有真实回放证据，其余行在补上样本之前不得对外声称可用。
图例：✅ 已有回放证据 ｜ ⏳ 无证据（无批准不得声称可用）｜ ❌ 当前行为与决策冲突，待修

### 2.1 容器

| 容器 | demuxer（实测存在） | V1 状态 | 证据 |
|---|---|---|---|
| MP4 / MOV | `qtdemux` | 承诺 | ✅ `video/1.mp4`（HEVC/AAC） |
| MKV / WebM | `matroskademux` | 承诺 | ✅ 6 个 VP9/Opus 样本 |
| MPEG-TS | `mpegtsdemux` | 承诺（SRT 直播的承载容器） | ⏳ 无样本 |
| AVI / FLV / OGG / RTP / 裸 ES 等 | — | 显式拒绝 | ⏳ 拒绝码未实现 |

### 2.2 视频

| 编码 | 位深 / 传输特性 | V1 状态 | 证据 |
|---|---|---|---|
| H.264 | 8-bit SDR | 承诺 | ⏳ `avdec_h264`/`vtdec` 实测存在，无回放样本 |
| HEVC | 8-bit SDR（Main） | 承诺 | ✅ `video/1.mp4`，macOS 由 `vtdec_hw` 解出 |
| VP9 | 8-bit SDR（Profile 0） | 承诺 | ✅ 样本矩阵主力格式 |
| VP8 | 8-bit SDR | 承诺 | ⏳ 无样本（`vp8dec` 实测存在） |
| AV1 | 8-bit SDR | 实验 | ⏳ 仅 `av1dec` 存在性实测；不进 Golden Path，不作验收阻塞项 |
| HEVC Main10 / VP9 Profile 2 / AV1 10-bit 等 | ≥ 10-bit | 显式拒绝 | ❌ 当前静默降位后仍算成功（实测 A） |
| PQ / HLG 等 HDR 传输特性 | 任意位深 | 显式拒绝 | ⏳ 无样本；8-bit HDR 同样拒绝，颜色语义无法保证 |
| ProRes / DNxHD / MPEG-2 / VC-1 / JPEG2000 | — | 显式拒绝 | ⏳ 不在端侧采集主流范围内 |

### 2.3 音频

| 编码 / 布局 | V1 状态 | 证据 |
|---|---|---|
| AAC-LC | 承诺 | ✅ `video/1.mp4` |
| Opus | 承诺 | ✅ VP9 样本；pre-skip 差异已按轨道容差校准 |
| Vorbis | 承诺 | ⏳ 无样本（`vorbisdec` 实测存在） |
| 容器内 PCM | 承诺 | ⏳ 无样本 |
| AC-3 / E-AC-3 / DTS / TrueHD | 显式拒绝 | ⏳ 端侧采集不作为主流 |
| `channels > 2` | 显式拒绝（v1 只承诺 mono/stereo） | ❌ 当前 6 声道原样透传（实测 C） |

### 2.4 归一化目标（不随输入格式变化）

| 平面 | 目标 caps | 元素 |
|---|---|---|
| 视频 | `video/x-raw,format=RGBA` | `videoconvert` |
| 音频 | `audio/x-raw,format=F32LE` | `audioconvert` |

归一化目标保持不变；变化的是**在归一化之前先做准入判定**，而不是让 `videoconvert` 兜住一切。

## 3. 决策二：白名单之外一律显式拒绝

**规则：** 任何不在 §2 矩阵内的 `(container, codec, bit_depth, chroma, channel_layout, transfer)` 组合，
必须在 caps 协商阶段被判定为拒绝，并且**同时**满足：

1. 拒绝码进入 `ReplayReport.blockers`（该构建整体不支持）或
   `DecodedTrackStat.drop_reasons` / `decoded.failure_reasons`（该流不支持）**二者之一**；
2. 拒绝码是稳定字符串，不写自由文本，不复用 `unsupported_media_source` 这类宽泛错误；
3. 该轨道不得产生 `BufferDescriptor`，也不得让计数看起来像"流里本来就没有这条轨道"；
4. 禁止"只写日志"——`tracing::warn!` 是运维信息，不是契约（实测 B 的修法）；
5. 禁止降级成功——不接受"先降到 8-bit 再报成功"（实测 A 的修法）。

**拒绝码命名规范**（`unsupported_` 前缀 + 维度 + 取值）：

| 维度 | 示例 |
|---|---|
| 容器 | `unsupported_container_avi` |
| 编码 | `unsupported_codec_prores` |
| 位深 | `unsupported_bit_depth_10bit` |
| 色彩/传输特性 | `unsupported_transfer_characteristics_pq` |
| 声道布局 | `unsupported_channel_layout_multichannel` |
| 轨道结构 | `unsupported_track_layout_multiple_video` |
| 时间基准 | `unknown_timing_base`（对应 `MediaTrack.timing_known=false`） |

## 4. 决策三：准入判定落在 caps 协商阶段

新增 `crates/media/src/capability.rs`，把矩阵写成数据而不是散落的 `if`：

```text
MediaFormatClass { container, codec, bit_depth, chroma, channel_layout, transfer }
classify_caps(&gst::Caps) -> Verdict::{Admitted, Rejected { code, detail } }
```

**约束：**

- 判据必须在 **caps 协商阶段**产生，也就是在 `decodebin` 的 `pad-added` 回调里、
  在把 pad 连到归一化链之前。等到 `videoconvert` 之后再看，信息已经丢了（实测 A）。
- 需要位深/传输特性时，读的是**解码器输入 caps**（`video/x-h265, profile=main-10` 之类），
  不能只看 `pixel_format` 字符串。
- 现有 `classify()` 的 `Option<TrackKind>` 返回值不足以表达拒绝原因，需要同时返回
  `TrackKind` 与 `Verdict`；`None` 分支（非音视频 pad）也要落到显式计数上。
- 复用既有机制，不新造平行体系：进程级缺失进 `blockers`，
  流级拒绝进 `drop_reasons` / `failure_reasons`，与 `unavailable_reason` 的语义保持一致。

**验收方式（每个拒绝项一条负样本）：** 负样本可以合法地用 FFmpeg 合成
（如 `-pix_fmt yuv420p10le` 造 10-bit、`-af pan=5.1` 造多声道），
但必须在报告里标注为"拒绝路径验证样本"，**不得**作为任何正样本证据。

## 5. 决策四：解码主路径唯一，FFmpeg 只做探测与离线基线

**决策：** GStreamer 是唯一解码主路径，不变（ADR-003）。
需要额外格式覆盖时，**优先使用已安装的 `gst-libav`（`libav`）元素**，
不引入 `rsmpeg` / `ffmpeg-next` 这类第二套解码器。

**理由：** 现有的时间戳语义是按 GStreamer buffer 校准出来的——Opus pre-skip、
毫秒粒度的段边界回退、容器 edit list 的呈现原点。再引入一套解码器就是再引入一套 PTS 语义，
两套语义会在 descriptor 与 report 层互相污染，而且很难用测试证明"等价"。

**解码器选择必须可追溯。** `decodebin` 自动协商，实际选中哪个元素随平台变化，实测（2026-09-23，`macos-aarch64`）：

```console
$ GST_DEBUG=GST_ELEMENT_FACTORY:4 gst-launch-1.0 -q \
    filesrc location=video/1.mp4 ! decodebin ! fakesink sync=false
creating element "h265parse"
creating element "vtdec_hw"      # HEVC 走 VideoToolbox
creating element "avdec_aac"     # AAC 走 gst-libav
```

同一台机器上 `gst-inspect-1.0 avdec_hevc` **不存在**。也就是说：
macOS 的 HEVC 覆盖来自 VideoToolbox 而不是 libav；Linux 侧是否有 `avdec_hevc` /
`nvdec` / `nvv4l2decoder` 必须**逐主机实测**，不能从 macOS 结论外推
（ADR-008 的"跨平台结论必须标注平台与执行后端"）。

**因此：** 解码器元素名（如 `vtdec_hw`、`avdec_h264`）必须进入报告证据，
否则"这个格式在 macOS 上可用"这句话无法被复核。

**许可提醒（部署检查清单项）：** 本机 FFmpeg 是 `--enable-gpl` 构建
（实测 `ffmpeg 9.0.1 ... --enable-gpl ... --enable-libx264 --enable-libx265`）。
GPL 组件不得进入分发产物；`gst-libav` 同样受其底层 `libav*` 构建的许可约束。
发布产物必须验证 `ffmpeg -version` 的 `configuration` 行，而不是假定发行版默认值。

**可选纯 Rust 后端（评估结论，暂不引入）：** Symphonia 只覆盖音频解码，且同样会引入第二套
时间戳语义；若将来引入，只能作为**可选后端**并复用同一 descriptor/report 契约。
`audiobuffersplit`（实测存在）可以先不替换手写 segmenter——现有切段已有段边界证据，
替换属于 `docs/TODO.md` 第 3 节的优化项，不属于格式支持范围。

## 6. 决策五：两个契约缺口现在钉死

矩阵一旦承诺"8-bit SDR、单一视频轨"，就必须能**表达**违反它的输入，否则拒绝无从判定。
当前 `proto/common/v1/common.proto` 的 `BufferFormat` 只有
`pixel_format / width / height / strides / sample_rate / channels`，缺两组字段：

**(1) 几何：** `display_rotation_deg`、`pixel_aspect_ratio_num/den`。
手机竖屏素材与 anamorphic 素材现在会被当成"几何正确"处理，错误会一路传导到 OCR/VLM 输入。

**(2) 位深与色彩：** `bit_depth`、`color_primaries`、`transfer_characteristics`、`matrix_coefficients`。
没有这四个字段，实测 A 的降位就无法被表达，只能继续"看起来成功"。

配套规则：

- v1 只承诺 `display_rotation_deg ∈ {0, 90, 180, 270}` 且 SAR 为 1:1 或可显式上报；
  其他取值显式拒绝。
- 旋转必须在归一化阶段真正应用（`videoflip` 实测存在），并且报告中记录应用过的角度——
  下游模型拿到的帧必须是"呈现后"的画面，而不是未旋转的原始帧。
- `bit_depth` 记录**源**位深；`unsupported_bit_depth_*` 拒绝码记录被拒的那一位。
  两者都不是估算值，取不到就按"未知"表达，不得填默认值。

## 7. 决策六：时间基与帧率模式显式化

现有 `MediaTrack.timing_known` 只能表达"知道 / 不知道"，`DecodedTrackStat.timeline_offset_ms`
只覆盖 edit list 原点。需要补两项：

- **时间基：** `timescale_num/den`（容器声明的刻度），使 `pts_ms` 的取整来源可复核。
- **帧率模式：** `CONSTANT | VARIABLE | UNKNOWN`。现有 6 个样本**全部是 CFR**
  （见 [待办](../TODO.md) 待补样本），v1 不承诺 VFR 抽帧语义；
  但 v1 必须能**声明**一条轨道是 VFR 或 UNKNOWN，禁止把未知帧率当 CFR 处理。

`timing_known=false` 的轨道不得进入 timeline fusion（`media.proto` 注释已规定），
这一点在接入 VFR 前保持有效。

## 8. 决策七：新增一个格式的固定成本

增加一个格式 = 下面四件事，缺一件就不算支持：

1. `capability.rs` 矩阵加一行（含拒绝码的另一半）；
2. 一个**正样本**：真实授权素材跑通回放，进 `tests/fixtures/media/OPEN-SAMPLES.md` 或等效记录；
3. 一个**负样本**：验证相邻的拒绝码确实触发（合成素材允许，只用于拒绝路径）；
4. `docs/verification.md` 一条证据行（平台标识、解码器元素、计数自洽性）。

这条规则的作用是让"支持格式"与"有证据"永远等长，避免矩阵变成愿望清单。

## 9. 后果与最小实现清单

按顺序落地（每一步都能单独验收）：

1. `capability.rs`（矩阵 + `classify_caps`）与拒绝上报告警路径打通；
   先只覆盖**已有样本的相邻拒绝项**：10-bit、多声道、未知 pad。
2. `media.proto` 补 §6 的几何与位深/色彩字段、§7 的时间基与帧率模式，跑 `make proto`。
   迁移语义：只追加字段、不重编号、不改既有含义。
3. 解码器元素名进入报告证据（§5）。
4. 负样本入库 + `docs/verification.md` 记录；同步更新 `docs/implementation-status.md`。
5. 之后按矩阵逐行添加格式（每行四件事，§8）。

**在完成第 1–4 步之前：**

- 不得对外声称任何矩阵外格式"可用"；也不得把 §2 中标 ⏳ 或 ❌ 的行说成可用——
  这些行要么还没有回放样本（MPEG-TS、H.264、VP8、Vorbis、PCM），要么当前行为与决策直接冲突
  （10-bit、多声道）；
- `ReplayReport.golden_path_verified` 保持 `false`；
- `adaptive_sampling_not_implemented` 等 blocker 继续如实上报。

## 10. 未验证范围

- 本 ADR 的实测结论均在 `macos-aarch64`（GStreamer 1.28.7、FFmpeg 9.0.1）取得；
  Linux/NVIDIA 侧的解码器可用性未验证。
- 6 个回放样本全部是 CFR 且均为转码产物（见 [待办](../TODO.md) 待补样本），
  容器级 VFR、设备直出、断流重连仍无样本。
- 合成负样本（10-bit、5.1）只证明"当前会静默通过"，
  不证明拒绝码实现正确——拒绝码要有实现后重跑的记录才算证据。
