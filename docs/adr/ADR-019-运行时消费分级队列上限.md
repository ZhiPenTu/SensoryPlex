# ADR-019：运行时消费分级队列上限（准入，而不是改写）

**状态：** Accepted（2026-09-24）
**上游决策：** ADR-008（Apple Silicon 一等目标与内存分级"必须遵守"）、ADR-010（跨进程数据面安全边界）、ADR-011（保留窗口按种类分配）、ADR-015（macOS 常驻形态与统一内存分级）
**相关文档：** [实现状态](../implementation-status.md)、[验证记录](../verification.md)、[待办](../TODO.md)、[macOS 常驻手册](../runbooks/macos-resident.md)

## 1. 背景与问题

ADR-008 把"容量按统一内存规划"写成必须遵守的一条：*"16GB 机型不得默认并行加载 ASR + OCR + Fast VLM，
**队列上限与模型量化档位必须随内存容量分级**。"* ADR-015 把这句话落成了分级表与注入路径：
`tools/macos_resident.py` 按宿主统一内存渲染 `resident.env` 与 launchd plist，
`deploy/macos/bin/sensoryplex-media-run` 把分级值注入媒体作业。

但 ADR-015 §5 自认了一个缺口：**`queue_capacity` 只被校验，没有被运行时消费**。本轮把这条缺口核实并收口，
核实到的事实是：

| 事实 | 位置 |
| --- | --- |
| pipeline 的 `queue_capacity` 只在解析时校验（`> 65536` 报 `invalid_pipeline_capacity_or_stages`），没有任何代码用它设队列深度 | `crates/runtime/src/lib.rs` |
| `SENSORYPLEX_MEDIA_QUEUE_CAPACITY` / `SENSORYPLEX_MODEL_PARALLELISM` 在**全仓没有任何 crate 读取**（改动前 `grep` 无命中） | `crates/**` |
| 描述符之后的**真实**有界队列是保留表：`RetainPolicy::default()` 的 `retained_limit=32`，带 `--handoff-listen` 时取 `config.retained_limit` | `crates/media/src/handoff.rs`、`crates/runtime/src/main.rs` |
| 分级值与 pipeline 声明值的一致性只由 `probe` **报告**（"匹配 / 超过本档上限"），不改写配置 | `tools/macos_resident.py` |

于是有两条坏结局，而且都不会报错：

1. **越界照跑。** 16 GiB 机型（`small` 档上限 16）上，pipeline 声明 `queue_capacity: 32`、保留窗口按内置默认
   32 条跑——与分级完全无关。
2. **假"已生效"。** 读文档的人以为"队列已按分级调整"，而实际上没有任何执行点读过这个数。

## 2. 决策一：分级是**准入上限**，不改写、也不夹取

`replay` / `ingest` 在解析 pipeline 之后、打开媒体源之前读分级，并对**两件事**做准入：

- pipeline 声明的 `queue_capacity`；
- 本次运行**真正使用的保留窗口深度**（`--handoff-retained-limit`，没有该参数时是内置默认值 32）。

任一超过 `SENSORYPLEX_MEDIA_QUEUE_CAPACITY`，运行就以显式原因失败，**且不写报告**：

| 原因（稳定字符串） | 触发条件 |
| --- | --- |
| `queue_capacity_exceeds_tier_cap: declared=<n> tier_capacity=<n> tier=<name>` | pipeline 声明值超上限 |
| `retained_limit_exceeds_tier_cap: retained_limit=<n> tier_capacity=<n> tier=<name>` | 本次运行的真实队列深度超上限 |

为什么不是改写或夹取：

- **改写**会让配置文件与执行事实长期不一致，且与 `probe` 已锁定的"只报告、不改写"语义直接冲突
  （`tests/contracts/test_macos_resident_contract.py::test_pipeline_queue_capacity_is_reported_not_rewritten`）。
- **夹取**（`min(声明值, 上限)`）会悄悄改变队列语义：保留表按种类对半分配（ADR-011），窗口一变，
  单一种类上限、背压阈值与丢弃计数全都跟着变——这正是"禁止静默 fallback"要禁止的那类改动。
- 第二种越界（保留窗口）必须单独判定：只看 pipeline 声明值会漏掉"没按分级跑"的另一半——
  内置默认值 32 在 `small` 档（16）上本身就是越界。

## 3. 决策二：未注入、坏值、越界是三种不同的结果

| 输入 | 结果 |
| --- | --- |
| 变量缺失（开发机没有 `resident.env`） | 显式 `not_injected`：报告里带声明值与真实保留窗口，但**上限字段为 0**，绝不填一个"看起来合理"的默认值 |
| 空串 / `0` / 非数字 / 非 UTF-8 | `invalid_resident_limit: <VAR>`：`serve` 直接起不来，`replay`/`ingest` 直接不跑 |
| 超过上限 | 上面两个稳定原因，运行失败 |

报告字段是 `ReplayReport.media_queue` 与 `LiveIngestReport.media_queue`（本 ADR 追加的 proto），
内容为 `state`（`not_injected` | `admitted`）、`tier`、`declared_capacity`、`tier_capacity`、`retained_limit`。
因为越界的运行根本写不出报告，所以报告里**不可能**出现"被夹到上限的成功"。

命令行侧仍保持"分级是单一事实源"：`sensoryplex-media-run` 在 `source resident.env` **之前**拒绝调用方
预置 `SENSORYPLEX_RESIDENT_TIER` / `SENSORYPLEX_MEDIA_QUEUE_CAPACITY` / `SENSORYPLEX_MODEL_PARALLELISM`
（exit 2），与它已有的 `--handoff-retained-limit` 覆盖拒绝同义；随后把这三个变量**导出**给子进程——
运行时从环境变量读分级，与 launchd plist 注入的是同一组变量名。

## 4. 决策三：`serve` 只转述，不声称已执行

`DescribeCapabilitiesResponse.residency`（本 ADR 追加的 proto）上报进程读到的 `tier`、
`media_queue_capacity`、`model_parallelism`。它关掉了 ADR-015 §7 的一条记录（"没有把分级值回写进
`DescribeCapabilities`"），但语义必须写清楚：

- `serve` 不跑 pipeline，**没有队列可以设上限**，所以这里上报的是"进程读到了什么"，不是"已生效"；
- `SENSORYPLEX_MODEL_PARALLELISM` 目前**没有任何 worker 读它**，因此它是**已声明的预算**，
  不是实测并发。worker 侧按该变量限流仍是未完成项（`docs/TODO.md` §3）。

把这两个限制写进 proto 注释与本文，是为了避免下一个人把"端点报了 3"读成"并发已限流 3"。

## 7. 后果与仍未验证范围

- **已收口**：`queue_capacity` 从"只被校验"变成"被运行时消费"——越界的声明或保留窗口会让媒体作业直接失败，
  并把 `not_injected` / `admitted` 写进报告。ADR-015 §5 的缺口头条因此不再成立。
- **同一口径已接到事件链路（[ADR-027](ADR-027-事件链路分级背压与容器化常驻.md)，2026-09-24）**：
  relay 的 `--batch` 与消费的 `--consume-batch` 走的是**同一套语义**（越界拒绝启动、不夹取、
  缺变量是显式 `not_injected`、原因码与 Rust 侧逐字对齐），上限来自分级的**独立一列**
  `SENSORYPLEX_EVENT_QUEUE_CAPACITY`；本 ADR 的"媒体面"结论不因此改变。
- **仍未验证**：`SENSORYPLEX_MODEL_PARALLELISM` 依然只有"已声明"这一层事实，没有 worker 按它限流，
  也没有并发执行的端到端样本。
- **仍未验证**：`small` 档（16 GiB）与 Mac mini 各档位没有真机跑过；本轮全部证据来自
  `macos-aarch64` / M2 Max / 32 GiB 一台机器。linux-x86_64 未验证。
- **不在本轮范围**：`queue_capacity` 仍然不是"实际队列深度的来源"——真实深度由
  `--handoff-retained-limit`（包装脚本按分级注入）决定。本轮做的是**准入**，不是"用 pipeline 文件驱动队列"；
  后者会改变默认行为，需要单独决策。
- **既有现象（未修复，与本 ADR 无关）**：`sintel-trailer.480p.h264.mp4` 在 `tools/verify_replay.py`
  的 `check_track` 上失败——ffprobe 报 `duration_ms=52208`，解码侧视频 `last_end_ms=52209`，
  差 1 ms 导致 `last_end_ms <= duration_ms` 不成立。本轮不改解码/轨道统计路径，仅记录以备后续处理。
- `golden_path_verified` 恒为 false，本 ADR 不改变这一结论。
