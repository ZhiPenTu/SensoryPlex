# ADR-020：向量索引落库与检索闭环（index-worker 的 sink 语义）

**状态：** Accepted（2026-09-24）
**上游决策：** ADR-008（Apple Silicon 一等目标）、ADR-010（跨进程数据面安全边界）、ADR-012（模型插件与端侧推理边界）、ADR-017（BGE 文本向量与维度版本化）、ADR-019（运行时消费分级队列上限）
**相关文档：** [实现状态](../implementation-status.md)、[验证记录](../verification.md)、[契约](../contracts/README.md)、[待办](../TODO.md)

## 1. 背景与问题

ADR-017 把 BGE 插件刻意定成**不落库**：payload 里 `storage=inline_payload`、`vector_ref=null`。
本切片补上它后面的 sink：`services/index-worker`（`sensoryplex-index`）把插件产出的向量写进
向量库，并提供一个能把这批向量检索回来的闭环。五个必须回答的问题：

1. **谁是事实源？** 向量库里的行能不能直接当检索结果返回？
2. **什么算"落库成功"？** 写了就是成功，还是读回来确认才算？
3. **模型或维度换了怎么办？** 旧向量原地迁移，还是留在原地？
4. **命中了凭什么能返回？** 谁来保证一个命中不是越权、不是已经作废的记录？
5. **edge 形态到底跑哪种 Milvus？** 容器 standalone，还是本地文件形态？

本切片只承诺**链路语义正确**（写入确认、回查、拒绝可观察），**不承诺向量质量**，也不承诺
服务端 Milvus 与 `linux-x86_64`/Mac mini（见 §9）。

## 2. 决策一：PostgreSQL 是事实源，Milvus 只是索引；命中必须回查

向量库只回答"哪条 `embedding_id` 离查询最近"。一条命中要成为**结果**，必须同时满足
PostgreSQL 侧的三条：`embedding_record.state='ready'`、`material_unit` 行存在且
`status <> 'failed'`、并且 `source.owner` 等于当前 principal。查不到的回查不得当成
"没有命中"——它是**被丢弃的命中**，单独计数 `unindexed_hits`：

- 越权：另一个 principal 检索同一 collection（场景 4）→ `results=[]`、`unindexed_hits=2`；
- 作废：记录被改成 `failed`，但向量还在库里（场景 5）→ 不返回，且计入丢弃。

`embedding_record` 的 `vector_ref` 不是鉴权依据，Milvus 里的 `material_unit_id`/`stream_id`
也不是：两者都在**回查之后**才被信任。理由与 ADR-010 一致——向量库是数据面组件，
它的可见性不定义权限。

## 3. 决策二：collection 名 = `vector_index_key`；换模型/维度 = 新 collection

延续 ADR-017 的"维度是身份的一部分"，把它落成物理布局：

- collection 名就是 `vector_index_key`：`material_text_<模型 slug>_d<实测维度>_v<契约版本>`；
- 维度三方一致才允许写入——key 后缀声明的维度、payload 自称的维度、向量实际长度；
- 换模型或换维度得到另一个 collection，**旧向量留在旧 collection**，不原地迁移、不改写、
  不补零、不截断；
- 已存在的同名 collection 必须与当前契约**逐字段**一致（字段名/类型/宽度/主键/向量维度/
  索引类型/度量），任何一处不同 → `vector_collection_contract_mismatch`，
  而不是"尽力兼容"（场景 9）。

## 4. 决策三：先写向量、**读回来确认**，再置 `ready`

顺序是决策而不是实现细节：`pending` → (upsert → fetch 确认) → `ready`，任何一步失败都落到
`failed` 并带 `error_code`。迁移 `0003_embedding_index.sql` 把这条顺序写成**行本身的不变式**，
让"库没写成功但记录说可用"在结构上不可能：

- `state='ready'` ⇒ 必须同时有 `vector_ref` 与 `indexed_at`；
- `state='failed'` ⇒ 必须有 `error_code`；
- `state='ready'` ⇒ `error_code IS NULL`。

同一份输入重跑得到**同一个** `embedding_id`（`sha256(observation_id|material_unit_id|revision)`
前 32 位十六进制），因此 upsert 幂等：重跑不新增行、不改 `vector_ref` 形状（场景 6）。

**被拒绝的观测也要留痕。** 维度不符在写入前就被拒绝，但它已经具备了可信身份
（observation + material + revision + key），因此先落 `pending` 再标 `failed`：
否则"拒绝了"在库里查不到，等同于静默丢弃（见 §8 缺陷 3）。落库的 `dimension` 取
`vector_index_key` 声明的那一个，payload 自称的值**不写进事实行**，免得被篡改值污染身份。

## 5. 决策四：`vector_ref` 是逻辑引用，不是部署配置

`vector_ref = milvus://<collection>/<embedding_id>`：不含主机路径、不含端口、不含库名之外
的任何部署信息。Lite 形态的 `--uri` 是本地文件路径，服务端形态是 `http(s)://` 端点，
两者产生**同一个** `vector_ref`；换部署不会让已有记录失效。验收场景 10 直接在向量库里
grep 原文片段、主机路径与 DSN，必须一个都找不到。

## 6. 决策五：本切片验收用 **Milvus Lite（文件形态）**；standalone 容器未验证

V1 蓝图把 edge 端定为 Milvus Lite。实际取舍是被环境逼出来的，如实记录：

- 本机 Docker Hub **不可达**（`docker pull milvusdb/milvus:v2.5.10` →
  `Get "https://registry-1.docker.io/v2/": EOF`），因此
  `deploy/compose/docker-compose.vector.yml` 里的 Milvus standalone **拉不下来、起不来**；
  quay.io 的 etcd 与 pgsty 的 MinIO 镜像在本地存在，但缺 Milvus 本体，栈不完整；
- 因此本切片所有验收都跑在 **Milvus Lite** 上，**standalone/服务端形态未经向量写入与检索验收**，
  文档与状态表不得把它写成可用；
- 两种形态共用同一套 `MilvusClient` API 与同一份 collection 契约，所以换形态是部署配置变更，
  不是代码分叉——但这条推论**没有实测证据**，只登记为后续验收项。

## 7. 决策六：Lite 是**单写进程**；目录被占用是 `vector_store_locked`（可重试）

Milvus Lite 对数据目录 `{data_dir}/LOCK` 加 advisory `flock`，同机另一个进程持有时本进程
打不开。这是 edge 形态的真实容量约束，必须显式表达，而不是让它伪装成"路径写错了"：

- 打开前按**同一个锁文件**预检（`milvus_lite.db.LOCK_FILENAME`），拿不到锁 →
  `vector_store_locked`，detail 只写文件名（不带主机路径）；
- 不重试、不降级、不换路径、不静默排队；持有者退出后同一目录立即可用（场景 11 两段都验）；
- 为什么不用异常文本判断：pymilvus 把 Lite 的失败包成笼统的
  `ConnectionConfigException("Open local milvus failed")`，而 `DataDirLockedError` 的异常链
  断在起本地服务的线程里——**只看异常文本或异常链都会退化成"什么都叫 unavailable"**。

## 8. 本轮暴露并修掉的真实缺陷（不是"一次就过"）

1. **回查 SQL 引用了不存在的列**：`material_unit` 的列是 `revision`，
   查询里却写 `m.material_revision` → 真实 PostgreSQL 直接
   `UndefinedColumn: column m.material_revision does not exist`。只有对着真库真迁移跑才会暴露，
   单元测试/mock 会全部放过。
2. **契约不符被兜底 `except` 吞掉**：`ensure_collection` 的通用异常包装把
   `IndexContractError` 变成 `vector_collection_create_failed`，稳定原因码在最后一跳被改写。
   现在契约错误与存储错误一起直接上抛。
3. **被拒绝的观测不留痕**：维度守卫在 `begin_pending` 之前抛出，于是"拒绝了"在库里查不到。
   现在先落 `pending` 再标 `failed`（见 §4）。
4. **锁冲突被读成"库不可用"**：见 §7，改成锁文件预检。
5. **验收脚本自身的进程边界**：Milvus Lite 的目录锁是**进程级**的，父进程开过的目录子进程
   再也打不开——而场景 9 要验的正是"子进程打开漂移 collection"。漂移 collection 该由
   子进程建，父进程不碰该目录（`tools/verify_index.py::stage_drifted_collection`）。

## 9. 后果与仍未验证范围

已落地：`services/index-worker`（`index`/`search`/`inspect` 三个显式子命令 + `pymilvus`/
`milvus-lite` 依赖）、迁移 `0003_embedding_index.sql`、`tools/verify_index.py`（11 个场景）、
`make index-check`、契约测试 `tests/contracts/test_index_worker_contract.py`。

**仍未验证（不得声称完成）：**

- **常驻消费（本切片内）未接线**：本切片只有显式调用，因此**没有**"看起来在跑"的 index-worker
  容器。[ADR-024](ADR-024-outbox分发接线与消费去重边界.md) 接上了**发布这一跳**（outbox →
  JetStream + 消费去重原语），[ADR-025](ADR-025-常驻消费循环与sink接线.md) 随后接上了**消费这一跳**
  （`cli serve --consume`，消费与检索面同进程——理由正是本 ADR §7 的 Milvus Lite 目录锁），
  并通过 `make consume-check`；当时那条"要先补 observation 事件契约"的判断被 ADR-025 改写为
  "事件只是通知，按 `payload_ref` 回查事实"；
- **网关语义检索（本切片的缺口已收口）**：`mode=semantic` 已按
  [ADR-023](ADR-023-网关语义检索接线与索引检索面.md) 接上常驻检索面（API 不打开向量库）；
  RRF/混合检索与相关性校准**仍未做**——`distance` 是单路 COSINE 距离，不是相关性分；
- **向量质量未验收**：没有带参考文本的检索样本，因此**没有** recall/MRR/排序基准；
- **共享向量去重未做**：同一段文字被多个 material 引用时会各存一份向量（`embedding_id`
  含 material 作用域，这是幂等与多对多引用的代价）；
- **服务端 Milvus 未验收**（Docker Hub 不可达）、`linux-x86_64` 与 Mac mini 未验证；
- 未做 worker 侧的 durable 幂等与崩溃回收、lease/事务边界之外的补偿；
- `golden_path_verified` 仍恒为 false。
