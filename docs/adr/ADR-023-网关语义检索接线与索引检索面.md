# ADR-023：网关语义检索接线与索引检索面（进程独占、同源守卫、状态码与 retryable 分野）

**状态：** Accepted（2026-09-24）
**上游决策：** ADR-010（跨进程数据面的安全边界）、ADR-017（BGE 文本向量与维度版本化）、ADR-019（运行时消费分级队列上限）、ADR-020（向量索引落库与检索闭环）
**相关文档：** [实现状态](../implementation-status.md)、[验证记录](../verification.md)、[待办](../TODO.md)、[契约与查询语义](../contracts/README.md)

---

## 1. 背景与问题

ADR-020 把向量**落库并检索回来**做完了，但接口面只到 `sensoryplex-index` 的显式调用；
`docs/TODO.md` 与 ADR-020 §9 都记着同一句缺口：**网关 `mode=semantic` 仍返回 501**。
把 501 换成真实检索时，第一个约束不是排序质量，而是**谁能打开向量库**：

| 事实 | 位置 |
| --- | --- |
| Milvus Lite 的数据目录是**进程独占**的（目录 flock），被别的进程持有即 `vector_store_locked` | ADR-020 §7 |
| 因此"持有索引的进程"只能是**一个**常驻进程，而 API 是会被横向复制的无状态服务 | ADR-013 |
| API 进程自己去开同一个数据目录 → 直接撞锁，且**换路径不解决问题**（那只是看不见索引） | ADR-020 §7 |
| 检索必须"编码查询 → 近邻 → 回查 PostgreSQL 的 ready/owner"三段都做，缺一段就会返回越权或已作废的命中 | ADR-020 §2 |

于是有一句极易被写错的话：**"网关接上语义检索"不等于"网关自己检索"**。
如果 API 自己装配一份 BGE、自己连向量库，得到的是：三处重复的模型装配（ADR-017 的维度版本化身份
会在三处各自对账）、一个必然的目录锁冲突，以及一个"最后一个进程碰巧拿到锁"的随机 layout。

## 2. 决策一：检索面就是索引持有者，API 只做"转发 + 事实水合"

新增 proto 包 `index/v1`（`proto/index/v1/index.proto`）：`IndexSearchService.SearchSemantic`
请求只带 `query` / `principal` / `vector_index_key` / `limit`，响应给 `hits`（引用 + 距离）、
`collection`、`index_version`、`unindexed_hits`、`query_model_release_id` / `query_dimension`
与 `IndexFailure{reason_code, detail, retryable}`。

`services/index-worker` 的 `cli serve` 成为**常驻检索面**：它打开向量库后一直持有，
用 `pymilvus`/Milvus Lite 做近邻，用 PostgreSQL 做事实回查（`state='ready'` + material 存在
且未失败 + `source.owner == principal`），被丢弃的命中计入 `unindexed_hits`。

API 侧（`services/api/.../infrastructure/semantic.py`）只做三件事：调检索面、把**稳定原因码
原样上抛**、按 `(material_unit_id, revision)` 重新水合事实。两条写死的边界：

- **命中不是事实源，也不是鉴权依据**：API 拿到的是引用，素材本体只从 PostgreSQL 水合
  （ADR-020 §2）。水合不出来的命中单独计入 `unresolved_hits`——结果集**不静默变小**。
- **事实水合只有一处实现**：检索面不水合素材本体，`materials.py` 不被复制成第二份。

## 3. 决策二：查询向量用插件自己的 `Start`，并用同源守卫挡住混装

查询文本要编码成与索引向量**同一份模型身份**的向量，否则距离没有可比性。
本切片的做法是**引入 BGE 插件当库调用**（`EmbedPlugin.configure` 的同一段装配），
而不是在检索面里复制第二套 ONNX 装配：

- 对账口径是 `model_release_id`（`bge:<模型>@<权重摘要前缀>`，ADR-017）；
- **collection 级**同源守卫：`embedding_record` 里该 collection 的 release 必须**唯一且等于**
  本次查询编码器，否则 `vector_index_model_release_mixed` / `query_model_release_mismatch`，
  **整请求拒绝**（不是"挑一部分近似"）；
- 刻意不按 principal 过滤：collection 是所有 owner 共用的，混进另一个 release 的向量会让
  **所有人**的距离失去可比性；
- 启动时还要对一次 `query_encoder_index_key_mismatch`（编码器推出来的 collection 与服务持有的
  不是同一个即拒绝）：拿 A 模型的查询向量搜 B 模型的 collection 是配置错误，不是降级。

## 4. 决策三：检索面的鉴权与准入都必须显式

检索面一旦跨容器接入就要显式开端口，因此：

- **共享令牌 + 常量时间比较**（`hmac.compare_digest`）：`authorization: Bearer <token>`；
  缺失与带错**一律** `PERMISSION_DENIED`，不区分"没带"与"带错"（不给出可用于探测的半句信息）；
- **没有令牌不允许启动**（`index_auth_token_required`），令牌少于 32 字符不允许启动
  （`index_auth_token_too_short`）；
- `bind` 默认 `127.0.0.1:50077`——回环是默认值，跨机接入是**显式**决定；
- 准入逐项显式：空/超长查询 `invalid_query`、空/超长 principal `invalid_principal`、
  collection 与本次服务不符 `vector_index_key_mismatch`、超过 100 条 `invalid_limit`。
  没有"默认值猜测"这一层。

## 5. 决策四：HTTP 状态码只表示"失败落在哪一环"，`retryable` 是**独立**标记

三条失败形态必须能被区分，且不得互相冒充：

| 形态 | 原因码 | HTTP | `retryable` |
| --- | --- | --- | --- |
| 网关压根没走到检索面：未配置 | `semantic_search_unavailable` | 503 | false |
| 网关压根没走到检索面：令牌不符 | `semantic_index_unauthenticated` | 503 | false |
| 网关压根没走到检索面：连不上/超时/被限流 | `semantic_index_unreachable` | 503 | true |
| 检索面答了，但答的不是本契约 | `semantic_index_protocol_error` 等 | 502 | false |
| 检索面自报 `retryable=false` 的码 | 原样上抛（如 `vector_collection_contract_mismatch`） | 502 | false |
| 检索面自报 `retryable=true` 的码 | 原样上抛（如 `vector_store_locked`） | 503 | true |

两条推论必须写死：

- **503 不等于"重试就好"**：`semantic_search_unavailable` 与 `semantic_index_unauthenticated`
  都是 503 却不可重试——令牌配错了，重试一万次也还是错的；
- **`retryable` 不能反推状态码**，反之亦然。HTTP 状态码表达不了"不可重试的 503"，
  所以 `contracts.fail(status, reason, retryable=...)` 允许调用方覆盖默认口径
  （默认仍是"429/503 可重试"）。该标记只挂在 `HTTPException.headers` 上由本项目的错误处理器
  在**进程内**消费，**不出现在响应头里**。
- **原因码原样上抛**：ADR-020 §8 记录过"最后一跳改写原因码"的缺陷（把契约不符伪装成可重试的
  `vector_search_failed`），这里不再重犯。API 自有的码（`semantic_search_unavailable`、
  `semantic_index_*`）与检索面的码是**两套词汇**，混用会把"没部署"读成"索引坏了"。

## 6. 决策五：本切片只做**纯语义**，越界条件显式拒绝

- `mode=semantic` 只接受 `query` + `limit`；`stream_id` / `modalities` / `tags` /
  `start_ms` / `end_ms` / `min_confidence` **显式 422** `semantic_filters_not_supported`。
  静默忽略筛选条件会返回"像是筛过"的结果，那比拒绝更糟。
- 空查询在 API 侧即拒绝（`invalid_query`）：它是调用方输入错误，不该变成一次"上游失败"。
- **keyword 模式不排名**：`hits` 必须为空（"没有排名"与"排名为 0"不同），
  `index_version=postgres-literal-v1`；semantic 的 `hits` 与 `materials` **同序同长**。
- **RRF / 混合检索 / 相关性校准未做**。响应里的 `distance` 是 COSINE **距离**（越小越近），
  不是置信度，不得当排序分或置信度使用。
- 能力上报只报**配置事实**：配了 `index_search_endpoint` 才报 `semantic_search` 可用
  （`unavailable_reason` 为空），没配就报 `semantic_search_unavailable`——**不再用
  `semantic_index_not_configured`，也不再是 501**。"配了"不等于"链路通"，后者由检索本身回答。
- 终结点与令牌**要么都不配、要么都配齐**（半配置不允许启动：`index_search_token_required`、
  `index_search_endpoint_required`），且终结点必须是 gRPC target（`host:port`），写成 URL 直接
  拒绝（`index_search_endpoint_invalid`）——否则会被静默当成域名。

## 7. 验收（`make semantic-check`）

`tools/verify_semantic_search.py` 在主机侧跑（Milvus Lite 数据目录与 HF 权重只存在于主机，
理由同 `index-check`）：真实 BGE 插件进程编码三段真实文本 → 真实 Milvus Lite 落库 →
起**常驻检索面**（持有向量库的唯一进程）→ 真实 API 走 HTTP 检索并水合事实。13 个场景全过：

| # | 场景 | 断言要点 |
| --- | --- | --- |
| 1 | 真实观测落库 | PostgreSQL 侧 `ready` 行数与 release 数、另一个进程 `inspect` 的可见行数与维度一致 |
| 2 | 检索面必须带令牌 | 不带令牌的 `serve` 拒绝启动（`index_auth_token_required`） |
| 3 | 启动常驻检索面 | 报告 `address` / `collection` / `vector_index_key` / `index_version` / `encoder` |
| 4 | 端到端语义检索 | 真实编码 + 真实近邻 + 真实水合；`mode=semantic`、`hits` 与 `materials` 同序同长、距离有界 |
| 5 | 非 owner 命中被丢弃 | 越权命中不进结果、计入 `unindexed_hits`，**不表现成"没有命中"** |
| 6 | keyword 不排名 | `hits` 为空且不带语义字段 |
| 7 | 线上真正传的东西 | 裸 gRPC 抓包：不外泄路径/令牌/权重目录等受控引用（AGENTS.md 的日志约束） |
| 8 | 令牌不符 | 503 + `semantic_index_unauthenticated` + `retryable=false`（配置问题，不是"稍后重试"） |
| 9 | 检索面不可达 | 503 + `semantic_index_unreachable` + `retryable=true`，且响应里**没有** `materials` |
| 10 | 未配置 ≠ 曾经 501 | 能力表报 false/`semantic_search_unavailable`；配了就报 available 且 reason 为空 |
| 11 | 同源守卫两种形态 | 整库另一个 release、同库混装 → 各自稳定码、整请求拒绝；清掉外来行后恢复 |
| 12 | collection 契约漂移 | **启动时**即拒绝（`vector_collection_contract_mismatch`），不留到第一次查询 |
| 13 | 目录锁 + 停止后可用 | 第二个进程被拒（`vector_store_locked`）；前一个优雅停止后立刻可再起 |

同切片的其余证据：`tests/contracts/test_semantic_search_contract.py`（契约面：字段、
keyword/semantic 字段分离、单稳定码 + retryable 判定、detail 有界且不含路径、
准入逐项拒绝、Bearer 鉴权不区分"没带/带错"、同源守卫、HTTP 状态码与 retryable 分野、
API 与检索面词汇不混用）与 `tests/integration/test_semantic_search.py`（真实 gRPC 往返 +
真实 PostgreSQL 水合：水合与距离、丢弃与未水合分开计数、原因码逐字到达、
令牌不符/不可达、越界条件在调用检索面之前就被拒绝、未配置/已配置的能力上报、keyword 不带语义字段）。

## 8. 顺带修掉的既有缺陷

四个都是**真链路才暴露**的，记在案以免下次重犯：

1. **`stable_code` 白名单太窄**：`execution_provider_not_selected:CPUExecutionProvider`
   这类"码 + 冒号参数"被拒。收紧为 `^[a-z][a-z0-9_]{0,59}(:[A-Za-z0-9_.!<>=-]{1,40}){0,2}$`
   并加 `MAX_STABLE_CODE_LENGTH=120`——仍然有界，但不把合法码误判成脏数据。
2. **HTTP 状态码口径**：见 §5。改动前"是不是 503"被当作"是否可重试"的唯一表达，
   于是"令牌配错"与"服务暂时不可用"在客户端看来一模一样。
3. **`service._session_options(database_url)` 覆盖了 DSN 的 `options`**：连接池原来用
   `options=-c statement_timeout=...` **覆盖**调用方给的会话设置，静默丢掉隔离 schema 用的
   `-c search_path=...`，表现为"连上了却查不到表"（`relation "embedding_record" does not exist`）。
   改成**追加**。
4. **`cli.run_serve` 启动时 `index.ensure_collection()`**：漂移的 collection 原来拖到第一次查询
   才失败，而那时的失败被包装成可重试的 `vector_search_failed`——把配置事实伪装成瞬时故障，
   运维会被指向错误的排查方向。现在启动即拒（`vector_collection_contract_mismatch`）。
5. **`make gateway-smoke` 的语义断言写在旧契约上**：`services/gateway` 内嵌 `sensoryplex_api`
   （Dockerfile 把 `services/api` COPY 进 gateway 镜像），但断言仍写着 `mode=semantic == 501`，
   于是"旧实现 + 旧断言"自洽地 PASS——一个只证明"两个旧东西还一致"的冒烟检查。同步改成
   ADR-023 口径（未配置 → 503 + `semantic_search_unavailable` + `retryable=false`；空查询 → 422）
   并重建 gateway 镜像后才验到真行为。**API 的契约/行为改动必须同时重建 gateway 镜像。**

## 9. 后果与仍未验证范围

已落地：`proto/index/v1/index.proto` 与生成代码、`services/index-worker` 的
`query_encoder.py` / `service.py` / `cli serve`、`services/api` 的
`infrastructure/semantic.py` + `settings` / `business` / `app` 接线、`SearchResponse` 的
`hits`/`unindexed_hits`/`vector_index_key`/`unresolved_hits`、`tools/verify_semantic_search.py`
+ `make semantic-check`、契约与集成测试、console 的原因码文案。

**仍未验证（不得声称完成）：**

- **常驻 index-worker 消费（NATS/outbox → sink）仍未接线**（ADR-020 §9 的同一缺口，属于后续切片）：
  检索面是常驻的，但"向量怎么进来"仍只有显式调用；
- **RRF / 混合检索 / 相关性校准未做**，`distance` 不是相关性分；筛选条件只在 keyword 模式生效；
- **向量质量仍未验收**：没有带参考文本的检索样本 → 没有 recall/MRR/排序基准；
- **服务端 Milvus 拓扑未验收**（本机 Docker Hub 不可达），`linux-x86_64`、Mac mini 与跨机未验证；
- **检索面跨机部署未验证**：本切片只在本机回环上验收，令牌 + 回环默认值是跨容器接入的**前置条件**，
  不是"跨机已验收"；
- 检索面**不做** durable 幂等、崩溃回收与限流外的排队补偿；`max_concurrency` 是固定上限；
- `golden_path_verified` 仍恒为 false。
