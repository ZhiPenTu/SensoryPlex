# ADR-011：保留窗口按 buffer 种类分配

**状态：** Accepted（2026-09-23）
**上游决策：** ADR-009（媒体格式支持矩阵与显式拒绝语义）、ADR-010（跨进程数据面的安全边界与可见性）
**相关文档：** [实现状态](../implementation-status.md)、[验证记录](../verification.md)、[契约](../contracts/README.md)、[待办](../TODO.md)

## 1. 背景与问题

M3 的保留表（`crates/media/src/handoff.rs`）是一张**所有 buffer 种类共用**的 FIFO：
视频帧、音频段、以后可能的其他来源都排在同一条队列里，总量受 `retained_limit` 约束，
溢出按 `handoff_backlog_full` 拒绝。

在做 M2 背压可观察、用**用户自己的 OBS 直播**（`live/obs`）做真实输入验收时，
这个设计暴露出一个只靠单元测试和文件回放发现不了的缺陷：

| 观察项 | 修复前（10 秒 OBS 直播窗口，`retained_limit=32`） |
| --- | --- |
| 保留表内容 | `retained=32/32`，**32 条全部是 `audio_pcm`** |
| 消费者拿到的视频 | `video_buffers=0` |
| 消费者进程 | `handoff_worker.py` 退出码 1，断言 `listing.has_video` 失败 |
| 丢弃 | `dropped=502`，`drop_kinds=audio_pcm:500,video_frame:2` |

原因是**生产速率不对称**：实时流里音频按 ~47 Hz 产生 PCM 段（5 秒切段前的入队频率远高于视频），
而视频帧经 M1 自适应抽帧后 keep 只有几 Hz。先到的种类在几个采样周期内就把整张表占满，
**视频帧一帧也交不出去**——而"表满了"这件事本身并不违反任何单进程不变量，
只有真实直播输入才会把它暴露出来。

结论：**总上限不能同时充当公平性保证**。一张共用表在速率不对称时必须有一条**按种类的第二重上限**。

---

## 2. 决策一：保留表分两层上限，单一种类最多占一半

- 保留表保留总上限 `retained_limit`（不变，上限仍 `<= 4096`），新增单一 buffer 种类的上限：

  ```rust
  pub fn retained_kind_limit(retained_limit: usize) -> usize {
      (retained_limit / 2).max(1)
  }
  ```

- `retain()` 里按顺序判两重有界，**先判种类配额，再判总上限**：
  某一 kind 的计数 `>= retained_kind_limit` 时，以独立拒绝码 `handoff_kind_quota_full` 拒绝；
  否则再走原来的 `handoff_backlog_full` / `arena_capacity_exceeded`。
  顺序保证"配额满"不会被误报成"表满"，报告里能区分这两种有界行为。
- `max(1, ...)` 保证极小上限（例如 `retained_limit=1`）下配额至少是 1，
  不把表变成"永远拒绝一切"的结构——`the_backlog_and_the_arena_are_both_bounded`
  用 `limit=1` 覆盖，仍然报 `handoff_backlog_full`。

## 3. 决策二：窗口组成必须可观察，不能只报总数

只报总深度会让人把"表还有富余"当成"各类都有位置"。因此 `HandoffStats` 增加三个字段
（`proto/media/v1/handoff.proto`，已 `make proto`）：

- `retained_kind_limit`：本运行的种类配额（= `max(1, retained_limit/2)`）；
- `retained_by_kind`：窗口当前由哪些 kind 组成、各多少条（`map<string, uint64>`）；
- `retained_kind_peak`：单一种类的水位高水位（不是总表高水位）。

并新增独立拒绝码 `handoff_kind_quota_full`，加入 `CAPACITY_REJECTIONS`（生产侧视为正常有界行为，
不当作故障）。`crates/runtime/src/handoff_service.rs` 把它映射为 `ResourceExhausted`。

## 4. 决策三：背压报告给出三条队列，降级先于拒绝

`BackpressureReport`（`proto/media/v1/media.proto`）的 `queues` 从两条变三条，覆盖两级保留上限：

| 队列 | 单位 | 含义 |
| --- | --- | --- |
| `handoff_retained_table` | items | 保留表总深度 / 高水位 / 总上限 |
| `handoff_retained_kind` | items | **最深的单一种类**深度 / 高水位 / 种类配额 |
| `handoff_arena_bytes` | bytes | 共享段已用 / 峰值 / 容量 |

- `QueueWatermarks` 增加 `retained_kind`，`PressureLevel` 由"总表 + arena"再叠加"最深的单一 kind"决定，
  任一维度越过 `degraded_percent`（默认 50%）即进入 `Degraded`，达到容量即 `Saturated`。
- `dropped_total == Σ drop_reasons == Σ drop_kinds` 恒等式仍然成立（原因是三种容量码，种类按 kind 分账）。
- 处理顺序仍是**先降速、再拒绝**：`decode.rs::accept()` 在抽帧前观测水位，
  `Degraded` 时放大采样最小间隔（`throttle_factor=4`，上限 `throttle_cap_ms=10 s`），
  `Saturated` 才会走到 `retain()` 的拒绝；被抑制但仍想 keep 的帧记 `SkipReason::BackpressureThrottled`。
- `BackpressureReport.observed=false` 是**如实声明"这次运行没有可观察的保留队列"**
  （例如未暴露数据面的 replay），不是"指标干净"。

## 5. 后果

- 收益：速率不对称的实时流下，视频帧不再被音频挤光。修复后同一路 OBS 直播
  （默认 `retained_limit=32`）消费者实测拿到 `video_buffers=2 audio_buffers=16`，
  `handoff_worker.py` 70 项检查通过；保留表自证有界
  `handoff_retained_table=18/18/32`、`handoff_retained_kind=16/16/16`，
  丢弃 537 条全部是 `handoff_kind_quota_full`（音频侧限流），`throttled=181`。
- 代价：**单一种类流只能用一半窗口**。纯音频或纯视频直播时，`retained_limit=32` 实际可用 16 条，
  在配额处开始拒保留。这是显式接受的取舍：公平性优先于单种类极限吞吐；
  需要更大窗口时提高 `retained_limit`（配额随之翻倍）。
- 后果：`tools/verify_handoff.py` 的大上限场景相当于"总窗口减半"，断言按 `max(1, limit/2)` 计算。
- 后果：契约新增字段是**追加**，`BackpressureReport` 仍在 `media/v1` 开发预览内，不破坏既有消费方。

**未验证范围（不得当作已完成）**

- GStreamer `queue` 元素与 `appsink max_buffers` **没有计数出口**，只在 `backpressure.rs`
  文档里说明覆盖范围；三条队列覆盖的是 arena 与保留表，不是 GStreamer 内部队列。
- 只在本机回环、`macos-aarch64` 上验收；`linux-x86_64`、Mac mini / 跨机未验证。
- 未验证小时级长直播下配额与高水位的行为，也未验证唯一 kind 长时间贴住配额时的尾延迟。
- 未验证"配额是否该按 track 而非按 kind 划分"（当前只有 `audio_pcm`/`video_frame` 两个 kind）。
- 模型 worker 尚未接入：本决策只保证"视频帧能交出去"，不保证语义链路可用（M8）。
